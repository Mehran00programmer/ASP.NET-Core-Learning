01

Solution و Project File

وقتی در Visual Studio یک پروژه جدید می‌سازید، در واقع دو فایل ساخته می‌شود که خیلی‌ها با هم اشتباه می‌گیرند: فایل Solution با پسوند .sln و فایل Project با پسوند .csproj. تفاوت این دو مثل تفاوت «کل پوشه کار» با «یک فایل داخل آن» است.

فایل Solution (.sln)

Solution یک فایل متنی ساده است که فقط نقش نقشه را دارد. لیست پروژه‌های عضو یک راه‌حل را نگه می‌دارد و به Visual Studio می‌گوید کدام پروژه‌ها با هم یک مجموعه را می‌سازند. خود Solution هیچ کدی ندارد و به‌تنهایی اجرا نمی‌شود؛ فقط ظرفی برای گروه‌بندی پروژه‌هاست.

چرا اصلاً وجود دارد؟ چون در پروژه‌های واقعی معمولاً بیش از یک پروژه داریم: مثلاً یک پروژه Web، یک پروژه Data برای دسترسی به دیتابیس، و یک پروژه Tests برای تست. Solution همه این‌ها را زیر یک چتر جمع می‌کند تا با یک کلیک بشود همه را با هم Build یا Debug کرد.

فایل Project (.csproj)

فایل .csproj قلب پروژه است. این فایل XML است و مشخص می‌کند:

  • هدف کامپایل روی کدام نسخه .NET است
  • چه پکیج‌های NuGet نصب شده‌اند
  • چه فایل‌هایی باید کامپایل شوند
  • تنظیمات مربوط به Nullable، ImplicitUsings و ...

یک فایل .csproj معمولی برای یک پروژه وب ASP.NET Core MVC این‌طور است:

XML — MvcMovie.csproj 
<Project Sdk="Microsoft.NET.Sdk.Web">

  <PropertyGroup>
    <TargetFramework>net8.0</TargetFramework>
    <Nullable>enable</Nullable>
    <ImplicitUsings>enable</ImplicitUsings>
  </PropertyGroup>

  <ItemGroup>
    <PackageReference Include="Microsoft.EntityFrameworkCore.SqlServer" Version="8.0.0" />
  </ItemGroup>

</Project>

سه نکته مهم در این فایل وجود دارد. اول، Sdk="Microsoft.NET.Sdk.Web" می‌گوید این یک پروژه وب است و ابزارهای مخصوص وب (مثل Razor) باید فعال باشند. دوم، TargetFramework نسخه .NET را مشخص می‌کند و تغییرش یعنی هدف کامپایل عوض می‌شود. سوم، PackageReference همان پکیج‌های NuGet نصب‌شده هستند که در بخش ۰۵ مفصل بررسی می‌شوند.

جمع‌بندی

Solution = ظرف گروه‌بندی پروژه‌ها. Project = تعریف واقعی یک پروژه با تنظیمات و پکیج‌هایش. اگر فقط یک پروژه دارید، Visual Studio باز هم یک Solution می‌سازد.

02

ساختار کامل پوشه‌ها و فایل‌ها

وقتی یک پروژه ASP.NET Core MVC می‌سازید، ساختار پیش‌فرض به این شکل است. این ساختار تصادفی نیست؛ دقیقاً بر اساس الگوی MVC و قراردادهای فریم‌ورک چیده شده است.

  • MvcMovie/
    • MvcMovie.slnفایل Solution
    • MvcMovie.csprojفایل Project
    • Controllers/کنترل‌کننده‌ها
    • Models/مدل‌ها
    • Views/نمایش‌ها
      • Home/Viewهای HomeController
      • Shared/Layout و Viewهای مشترک
      • _ViewImports.cshtmlusingهای مشترک
      • _ViewStart.cshtmlتنظیم Layout پیش‌فرض
    • wwwroot/فایل‌های استاتیک
      • css/استایل‌ها
      • js/جاوااسکریپت
      • lib/کتابخانه‌های JS
      • favicon.icoآیکون سایت
    • Program.csنقطه شروع برنامه
    • appsettings.jsonتنظیمات عمومی
    • appsettings.Development.jsonتنظیمات محیط توسعه
    • Properties/تنظیمات اجرا
      • launchSettings.jsonپروفایل‌های اجرا
    • Connected Services/سرویس‌های متصل
    • Dependencies/وابستگی‌ها (مجازی)

هر کدام از این‌ها را در ادامه این قسمت جداگانه بررسی می‌کنیم تا بفهمی هر فایل دقیقاً چه نقشی دارد. نکته مهم این است که MVC بر اساس «قرارداد بر پیکربندی» کار می‌کند: اگر پوشه‌ای به اسم Views/Home داشته باشی، فریم‌ورک خودش می‌داند که Viewهای HomeController آنجا هستند. لازم نیست جایی این را ثبت کنی.

03

wwwroot — فایل‌های استاتیک

پوشه wwwroot تنها پوشه‌ای است که محتوایش بدون هیچ پردازشی مستقیم به مرورگر کاربر فرستاده می‌شود. هر فایلی که داخل این پوشه باشد، از طریق آدرس مستقیم قابل دسترسی است. مثلاً اگر فایلی به آدرس wwwroot/css/site.css داشته باشی، مرورگر می‌تواند دقیقاً به آدرس /css/site.css برود و آن را دریافت کند.

به همین دلیل، این پوشه فقط برای فایل‌های استاتیک است: CSS، JavaScript، تصویر، فونت، آیکون، فایل‌های PDF و مشابه. فایل‌های کد (مثل .cs) و فایل‌های تنظیمات (مثل appsettings.json) هرگز نباید در wwwroot قرار بگیرند، چون امنیت خطرناکی دارد؛ هر کسی می‌تواند آن‌ها را دانلود کند.

ترتیب پوشه‌های داخلی wwwroot قرارداد خاصی دارد:

  • css/ — فایل‌های استایل
  • js/ — کدهای جاوااسکریپت نوشته‌شده توسط خودت
  • lib/ — کتابخانه‌های جاوااسکریپت (Bootstrap، jQuery و ...)
  • images/ یا img/ — تصاویر
  • favicon.ico — آیکون سایت

دسترسی به فایل‌های wwwroot در کد

در ASP.NET Core برای استفاده از این فایل‌ها در View از ~ استفاده می‌شود که به معنی wwwroot است. مثلاً:

HTML — View 
<link rel="stylesheet" href="~/css/site.css" />
<script src="~/lib/jquery/jquery.min.js"></script>
<img src="~/images/logo.png" />

برای اینکه این فایل‌ها واقعاً به مرورگر فرستاده شوند، ASP.NET Core به یک Middleware مخصوص نیاز دارد به نام UseStaticFiles که در Program.cs ثبت می‌شود. خوشبختانه در قالب پیش‌فرض MVC این کار انجام شده است. اگر این Middleware ثبت نشود، همه فایل‌های wwwroot با خطای 404 مواجه می‌شوند.

هشدار امنیتی

هرگز فایل حساسی مثل رمز، کلید API، فایل دیتابیس یا لاگ را در wwwroot نگذار. همه این‌ها به‌صورت Public در دسترس همه هستند.

04

appsettings.json — تنظیمات

appsettings.json فایل تنظیمات برنامه است. هر چیزی که «قابل تغییر در محیط‌های مختلف» باشد اینجا قرار می‌گیرد: رشته اتصال دیتابیس، کلیدهای API، تنظیمات لاگ، تنظیمات ایمیل، آدرس‌های سرویس‌های خارجی، و هر چیزی که نمی‌خواهی Hard Code کنی. این فایل به‌صورت JSON است و ساختار درختی دارد.

JSON — appsettings.json 
{
  "ConnectionStrings": {
    "DefaultConnection": "Server=.;Database=MvcMovie;Trusted_Connection=True;"
  },
  "Logging": {
    "LogLevel": {
      "Default": "Information",
      "Microsoft.AspNetCore": "Warning"
    }
  },
  "AllowedHosts": "*",
  "AppSettings": {
    "SiteName": "آموزش ASP.NET Core",
    "PageSize": 10
  }
}

محیط‌های مختلف

ASP.NET Core از مفهوم محیط اجرا پشتیبانی می‌کند. سه محیط رایج وجود دارد: Development (توسعه)، Staging (پیش‌تولید) و Production (تولید). برای هر محیط می‌توانی یک فایل جداگانه داشته باشی که تنظیمات appsettings.json اصلی را بازنویسی می‌کند:

  • appsettings.Development.json
  • appsettings.Staging.json
  • appsettings.Production.json

ترتیب خواندن این است که ابتدا appsettings.json خوانده می‌شود و بعد فایل محیط، روی آن اعمال می‌شود. مثلاً در محیط توسعه می‌توانی لاگ را کامل‌تر و رشته اتصال را به دیتابیس محلی تنظیم کنی، اما در تولید دیتابیس اصلی و لاگ محدودتر باشد.

خواندن تنظیمات در کد

برای خواندن تنظیمات از سرویس IConfiguration استفاده می‌شود. این سرویس به‌طور خودکار در DI Container ثبت شده و می‌توانی در Controller آن را در سازنده تزریق کنی:

C# — Controller 
private readonly IConfiguration _config;

public HomeController(IConfiguration config)
{
    _config = config;
}

public IActionResult Index()
{
    var siteName = _config["AppSettings:SiteName"];
    ViewBag.SiteName = siteName;
    return View();
}

به الگوی AppSettings:SiteName دقت کن. در فایل JSON، بخش‌های تو در تو با : از هم جدا می‌شوند. برای تنظیمات پیچیده‌تر می‌توانی کل یک بخش را به یک کلاس C# نگاشت کنی که در قسمت‌های بعدی یاد می‌گیری.

چرا این فایل مهم است؟

هر چیزی که «در محیط توسعه و تولید فرق می‌کند» باید در این فایل باشد، نه در کد. این کار باعث می‌شود بدون Rebuild کردن پروژه، فقط با تغییر appsettings.json، تنظیمات را عوض کنی.

05

Dependencies، NuGet و Frameworks

در Visual Studio زیر هر پروژه یک گره (Node) به نام Dependencies می‌بینی. این گره خودش یک پوشه فیزیکی نیست؛ یک نمای مجازی است که همه چیزهایی که پروژه به آن‌ها وابسته است را نشان می‌دهد. سه زیرشاخه اصلی دارد:

  • Frameworks — فریم‌ورک پایه .NET
  • Packages — پکیج‌های NuGet
  • Analyzers — ابزارهای تحلیل کد

Frameworks

این بخش می‌گوید پروژه روی کدام نسخه .NET کامپایل می‌شود. دقیقاً همان چیزی که در .csproj با تگ TargetFramework تنظیم شد. اگر نسخه را عوض کنی، همین بخش در Visual Studio هم تغییر می‌کند.

NuGet و Packages

NuGet فروشگاه (و سیستم مدیریت) پکیج‌های .NET است. هر پکیج یک کتابخانه آماده است که دیگران نوشته‌اند و می‌توانی استفاده کنی. به‌جای اینکه از صفر همه چیز بنویسی، پکیج نصب می‌کنی. مثلاً:

  • Microsoft.EntityFrameworkCore.SqlServer — برای اتصال به SQL Server
  • Newtonsoft.Json — برای کار با JSON
  • Serilog.AspNetCore — برای لاگ حرفه‌ای

نصب پکیج از سه راه ممکن است: از طریق NuGet Package Manager در Visual Studio، از Manage NuGet Packages با راست‌کلیک روی پروژه، یا از خط فرمان:

Terminal 
dotnet add package Microsoft.EntityFrameworkCore.SqlServer

وقتی پکیج نصب می‌شود، یک خط PackageReference به فایل .csproj اضافه می‌شود. یعنی NuGet و .csproj دو روی یک سکه‌اند.

Connected Services

این گره در Visual Studio برای اتصال به سرویس‌های خارجی است: Azure Storage، Azure Key Vault، gRPC، OpenAPI و مشابه. با راست‌کلیک روی Connected Services می‌توانی مستقیماً به یک سرویس متصل شوی و Visual Studio خودش تنظیمات و کدهای لازم را در پروژه اضافه می‌کند. برای پروژه‌های ساده معمولاً خالی است.

نکته

Dependencies یک پوشه فیزیکی نیست که بتوانی دستی محتوایش را ویرایش کنی. هر چیزی که اینجا می‌بینی، در واقع از .csproj خوانده می‌شود. برای تغییر وابستگی‌ها باید .csproj را ویرایش کنی یا از NuGet استفاده کنی.

06

Properties و launchSettings.json

پوشه Properties یک فایل مهم دارد: launchSettings.json. این فایل به Visual Studio و dotnet run می‌گوید وقتی دکمه Run را می‌زنی، برنامه چطور اجرا شود. این فایل فقط برای محیط توسعه است و در زمان انتشار (Publish) استفاده نمی‌شود.

JSON — Properties/launchSettings.json 
{
  "profiles": {
    "MvcMovie": {
      "commandName": "Project",
      "dotnetRunMessages": true,
      "launchBrowser": true,
      "applicationUrl": "https://localhost:7196;http://localhost:5071",
      "environmentVariables": {
        "ASPNETCORE_ENVIRONMENT": "Development"
      }
    },
    "IIS Express": {
      "commandName": "IISExpress",
      "launchBrowser": true,
      "applicationUrl": "http://localhost:5000"
    }
  }
}

مهم‌ترین بخش‌های این فایل

profiles — چند پروفایل اجرا تعریف می‌کند. وقتی Visual Studio را باز می‌کنی، در نوار بالا کنار دکمه Run می‌توانی بین این پروفایل‌ها سوئیچ کنی. مثلاً پروفایل MvcMovie (اجرای مستقیم) و پروفایل IIS Express (اجرای روی IIS Express).

applicationUrl — دقیقاً همان آدرسی است که مرورگر بعد از اجرا باز می‌کند و می‌توانی API را صدا بزنی. اگر پورت را تغییر بدهی، همان پورت ثبت می‌شود.

environmentVariables — مهم‌ترین بخش. متغیرهای محیطی که موقع اجرا ست می‌شوند. مهم‌ترینشان ASPNETCORE_ENVIRONMENT است که تعیین می‌کند برنامه در کدام محیط اجرا شود. اگر مقدارش Development باشد، فایل appsettings.Development.json خوانده می‌شود و صفحه خطای کامل نمایش داده می‌شود. اگر Production باشد، فایل appsettings.Production.json خوانده می‌شود و خطاها به کاربر نشان داده نمی‌شوند.

هشدار

این فایل فقط برای توسعه است. در سرور واقعی، ASPNETCORE_ENVIRONMENT را از طریق متغیرهای محیطی سیستم‌عامل تنظیم می‌کنند، نه از این فایل.

07

Program.cs و چرخه اجرا

فایل Program.cs نقطه شروع برنامه است. هر چیزی که در این فایل نوشته شود، قبل از شروع سرور اجرا می‌شود. در .NET 6 به بعد، این فایل به شکل Minimal Hosting Model نوشته می‌شود که کوتاه‌تر و خواناتره از نسخه‌های قبلی است.

یک فایل Program.cs پیش‌فرض برای پروژه MVC این‌طور است:

C# — Program.cs 
var builder = WebApplication.CreateBuilder(args);

// ۱. ثبت سرویس‌ها در DI Container
builder.Services.AddControllersWithViews();

var app = builder.Build();

// ۲. پیکربندی خط لوله (Middleware Pipeline)
if (!app.Environment.IsDevelopment())
{
    app.UseExceptionHandler("/Home/Error");
    app.UseHsts();
}

app.UseHttpsRedirection();
app.UseStaticFiles();
app.UseRouting();
app.UseAuthorization();

// ۳. تعریف الگوی مسیریابی
app.MapControllerRoute(
    name: "default",
    pattern: "{controller=Home}/{action=Index}/{id?}");

app.Run();

سه بخش اصلی Program.cs

۱. ثبت سرویس‌ها (Services)

builder.Services یک DI Container است. هر سرویسی که در برنامه استفاده می‌کنی باید یک‌بار اینجا ثبت شود. مثلاً AddControllersWithViews() می‌گوید «ASP.NET Core، سرویس‌های لازم برای MVC را فعال کن». اگر این خط را حذف کنی، Controller و View کار نمی‌کنند.

۲. خط لوله (Middleware Pipeline)

هر درخواستی که به برنامه می‌رسد، از یک زنجیره از Middlewareها عبور می‌کند. هر Middleware می‌تواند درخواست را ببیند، تغییر دهد، رد کند یا جواب بدهد. ترتیب ثبت مهم است، چون به همان ترتیب اجرا می‌شوند. مثلاً UseStaticFiles باید قبل از مسیریابی باشد، و UseAuthorization باید بعد از مسیریابی باشد.

مهم‌ترین Middlewareهای پیش‌فرض:

  • UseExceptionHandler — مدیریت خطا در محیط تولید
  • UseHttpsRedirection — ریدایرکت HTTP به HTTPS
  • UseStaticFiles — سرویس‌دهی فایل‌های wwwroot
  • UseRouting — تشخیص مسیر درخواست
  • UseAuthorization — بررسی دسترسی

۳. مسیریابی (Routing)

MapControllerRoute الگوی مسیر پیش‌فرض را تعریف می‌کند: {controller=Home}/{action=Index}/{id?}. این یعنی آدرس /Products/Details/5 به این شکل تفسیر می‌شود:

  • controller = Products
  • action = Details
  • id = 5 (اختیاری، به‌خاطر ?)

اگر آدرس خالی باشد (/)، مقدار پیش‌فرض اعمال می‌شود و درخواست به HomeController.Index می‌رود.

جمع‌بندی

Program.cs = ثبت سرویس‌ها + پیکربندی Middleware + تعریف مسیرها. هر چیزی که در این فایل نباشد، در برنامه وجود ندارد.

08

ساخت اولین Controller

Controller کلاسی است که درخواست‌ها را دریافت می‌کند و پاسخ می‌دهد. هر Controller از کلاس پایه Controller ارث‌بری می‌کند و نامش باید به Controller ختم شود (این قرارداد است).

روش اول: از منو

روی پوشه Controllers راست‌کلیک کن، Add → Controller را بزن و قالب MVC Controller - Empty را انتخاب کن. نام آن را HelloWorldController بگذار. این روش کد اولیه را خودکار می‌سازد.

روش دوم: ساخت دستی

می‌توانی یک فایل جدید در پوشه Controllers بسازی و کد را دستی بنویسی:

C# — Controllers/HelloWorldController.cs 
using Microsoft.AspNetCore.Mvc;

namespace MvcMovie.Controllers;

public class HelloWorldController : Controller
{
    public IActionResult Index()
    {
        return Content("سلام از HelloWorldController!");
    }
}

در این کد، سه چیز مهم است:

  • : Controller — ارث‌بری از کلاس پایه
  • Index() — یک اکشن که وقتی آدرس /HelloWorld باز شود اجرا می‌شود
  • Content() — یک متد از کلاس پایه که یک رشته ساده برمی‌گرداند

حالا پروژه را اجرا کن و به آدرس /HelloWorld برو. متن نمایش داده می‌شود. اما برگرداندن رشته خام کافی نیست؛ در بخش ۱۰ یک View واقعی برای آن می‌سازیم.

نکته

کلاس پایه Controller مجموعه‌ای از متدهای کمکی مثل Content()، View()، Json()، Redirect()، NotFound() و BadRequest() را فراهم می‌کند. به همین دلیل ارث‌بری از آن مهم است.

09

متدها و اکشن‌ها

به هر متد Public در یک Controller که یک IActionResult (یا Task<IActionResult>) برگرداند، یک اکشن می‌گویند. اکشن‌ها همان نقاط ورودی برنامه هستند که آدرس‌ها به آن‌ها نگاشت می‌شوند.

یک Controller می‌تواند چندین اکشن داشته باشد. مثلاً یک ProductsController می‌تواند اکشن‌های Index، Details، Create، Edit و Delete داشته باشد:

C# — ProductsController.cs 
public class ProductsController : Controller
{
    public IActionResult Index() { ... }
    public IActionResult Details(int id) { ... }
    public IActionResult Create() { ... }
    [HttpPost]
    public IActionResult Create(Product product) { ... }
    public IActionResult Edit(int id) { ... }
    [HttpPost]
    public IActionResult Delete(int id) { ... }
}

هر آدرس به این شکل به اکشن نگاشت می‌شود:

  • /Products → Index
  • /Products/Details/5 → Details(id: 5)
  • /Products/Create با GET → Create()
  • /Products/Create با POST → Create(product)

انواع خروجی اکشن

اکشن‌ها می‌توانند انواع مختلفی از خروجی برگردانند که همه از IActionResult ارث‌بری می‌کنند:

متدخروجی
View()نمایش یک View (HTML)
Content()متن ساده
Json()خروجی JSON
Redirect()ریدایرکت به URL
RedirectToAction()ریدایرکت به اکشن
NotFound()خطای 404
BadRequest()خطای 400
File()فایل برای دانلود
Ok()پاسخ موفق 200

اکشن‌های Async

اگر اکشن به عملیات طولانی (مثل دیتابیس یا API خارجی) دسترسی دارد، بهتر است آن را async تعریف کنی و Task<IActionResult> برگردانی. این کار باعث می‌شود سرور در طول انتظار، منابع را آزاد کند و بتواند به درخواست‌های دیگر جواب بدهد:

C# — Controller 
public async Task<IActionResult> Index()
{
    var products = await _db.Products.ToListAsync();
    return View(products);
}

ساخت اولین View

View فایل .cshtml است که با Razor نوشته می‌شود. Razor یک موتور قالب است که اجازه می‌دهد HTML و C# را با هم ترکیب کنی. با @ وارد کد C# می‌شوی و بقیه متن HTML خالص است.

قانون پیدا کردن View

وقتی در اکشن Index از return View(); استفاده می‌کنی، ASP.NET Core دنبال این مسیرها می‌گردد:

  1. Views/{Controller}/{Action}.cshtmlاول اینجا را چک می‌کند
  2. Views/Shared/{Action}.cshtmlاگر پیدا نشد، اینجا را چک می‌کند

پس برای HelloWorldController.Index، مسیر پیش‌فرض Views/HelloWorld/Index.cshtml است.

ساخت View برای HelloWorld

روی پوشه Views راست‌کلیک کن، پوشه‌ای به نام HelloWorld بساز (هم‌نام کنترل‌کننده) و داخل آن یک Razor View به نام Index.cshtml اضافه کن:

HTML — Views/HelloWorld/Index.cshtml 
<h2>صفحه Index از HelloWorld</h2>
<p>این اولین View ما است.</p>

حالا متد Index در کنترل‌کننده را طوری تغییر بده که به‌جای Content() از View() استفاده کند:

C# — HelloWorldController.cs 
public IActionResult Index()
{
    return View();
}

پروژه را اجرا کن و به /HelloWorld برو. صفحه HTML واقعی را می‌بینی.

فایل Views/Shared/_Layout.cshtml قالب مشترک همه صفحات است. هر View به‌طور پیش‌فرض داخل این قالب رندر می‌شود. Layout شامل هدر، منو، فوتر و لینک به فایل‌های CSS و JS است. با استفاده از @RenderBody() محتوای هر View داخل قالب قرار می‌گیرد.

فایل _ViewStart.cshtml هم به‌طور خودکار Layout = "_Layout" را برای همه Viewها تنظیم می‌کند تا لازم نباشد در هر View جداگانه بنویسی.

11

اتریبیوت‌ها

اتریبیوت‌ها برچسب‌های متادیتا هستند که بالای کلاس، متد یا پراپرتی می‌نویسی و به فریم‌ورک می‌گویند چطور رفتار کند. در ASP.NET Core MVC مهم‌ترین اتریبیوت‌ها این‌ها هستند:

اتریبیوت‌های HTTP

  • [HttpGet] — فقط درخواست GET
  • [HttpPost] — فقط درخواست POST
  • [HttpPut] — فقط درخواست PUT
  • [HttpDelete] — فقط درخواست DELETE
  • [HttpPatch] — فقط درخواست PATCH

مثال استفاده:

C# — Controller 
[HttpGet]
public IActionResult Create()
{
    return View();
}

[HttpPost]
public IActionResult Create(Product product)
{
    if (ModelState.IsValid) { ... }
    return View(product);
}

این الگو بسیار رایج است: یک اکشن Create برای نمایش فرم (GET) و یک اکشن Create برای دریافت داده فرم (POST). Action Selector بر اساس اتریبیوت، بین این دو تفکیک می‌کند.

اتریبیوت [Route]

مسیر سفارشی تعریف می‌کند. می‌توانی بالای کلاس بگذاری یا بالای متد:

C# — Controller 
[Route("api/products")]
public class ProductsController : Controller
{
    [Route("")]
    public IActionResult Index() { ... }

    [Route("{id:int}")]
    public IActionResult Details(int id) { ... }
}

در این مثال، Index به آدرس /api/products و Details به آدرس /api/products/5 نگاشت می‌شود. کلمه :int یک محدودیت مسیر (Route Constraint) است که می‌گوید فقط اعداد مجازند.

اتریبیوت [Authorize] و [AllowAnonymous]

[Authorize] می‌گوید فقط کاربران احراز هویت‌شده به این اکشن دسترسی دارند. [AllowAnonymous] برعکس، اجازه می‌دهد حتی کاربران ناشناس هم دسترسی داشته باشند (مثلاً برای صفحه ورود). این اتریبیوت‌ها در قسمت‌های بعدی مفصل بررسی می‌شوند.

اتریبیوت [ValidateAntiForgeryToken]

از حملات CSRF محافظت می‌کند. حتماً روی همه اکشن‌های POST که فرم دارند بگذار.

12

Action Selector

وقتی درخواستی می‌رسد، ASP.NET Core باید تصمیم بگیرد کدام اکشن را اجرا کند. به این فرآیند Action Selection می‌گویند. انتخاب بر اساس سه معیار انجام می‌شود:

  1. نام اکشن — باید با بخش action در URL یکی باشد
  2. اتریبیوت HTTP — باید با متد درخواست سازگار باشد
  3. پارامترها — باید با مقادیر موجود قابل پر شدن باشد

سناریوهای رایج

۱. دو اکشن با یک نام و دو اتریبیوت مختلف

C# 
[HttpGet]
public IActionResult Edit(int id) { ... }

[HttpPost]
public IActionResult Edit(Product product) { ... }

Action Selector بر اساس متد HTTP تفکیک می‌کند. GET به اولی و POST به دومی می‌رود.

۲. نام اکشن با نام متد فرق دارد

C# 
[ActionName("SignIn")]
public IActionResult Login() { ... }

با این اتریبیوت، آدرس /Account/SignIn به متد Login نگاشت می‌شود.

۳. غیرفعال کردن یک اکشن به‌عنوان مقصد

C# 
[NonAction]
public IActionResult Helper() { ... }

با [NonAction]، این متد دیگر به‌عنوان اکشن در دسترس نیست (فقط از داخل کد قابل صدا زدن است).

چرا مهم است؟

درک Action Selector کمک می‌کند وقتی دو اکشن مشابه داری، بدانی چرا یکی اجرا می‌شود و دیگری نه. همچنین جلوی AmbiguousMatchException را می‌گیرد که وقتی دو اکشن کاملاً یکسان تعریف کنی رخ می‌دهد.

ساخت اولین Model

Model کلاسی است که ساختار داده را تعریف می‌کند. مثلاً یک مدل ساده برای «فیلم»:

C# — Models/Movie.cs 
public class Movie
{
    public int Id { get; set; }

    public string Title { get; set; } = "";

    public string Genre { get; set; } = "";

    public decimal Price { get; set; }

    public DateTime ReleaseDate { get; set; }
}

اتریبیوت‌های اعتبارسنجی

Model می‌تواند اتریبیوت‌های اعتبارسنجی داشته باشد که به ASP.NET Core می‌گویند داده معتبر است یا نه:

C# — Models/Movie.cs با اعتبارسنجی 
using System.ComponentModel.DataAnnotations;

public class Movie
{
    public int Id { get; set; }

    [Required(ErrorMessage = "عنوان الزامی است.")]
    [StringLength(100, MinimumLength = 2)]
    public string Title { get; set; } = "";

    [Required]
    public string Genre { get; set; } = "";

    [Range(1, 1000, ErrorMessage = "قیمت باید بین ۱ تا ۱۰۰۰ باشد.")]
    public decimal Price { get; set; }

    [DataType(DataType.Date)]
    public DateTime ReleaseDate { get; set; }
}

این اتریبیوت‌ها خودشان کار نمی‌کنند؛ اما وقتی ModelState.IsValid را چک می‌کنی، ASP.NET Core خودکار همه اعتبارسنجی‌ها را اجرا می‌کند:

C# — Controller 
[HttpPost]
public IActionResult Create(Movie movie)
{
    if (!ModelState.IsValid)
    {
        return View(movie);
    }
    // ذخیره در دیتابیس
    return RedirectToAction("Index");
}
نکته

برای استفاده از این اتریبیوت‌ها حتماً using System.ComponentModel.DataAnnotations; را بالای فایل اضافه کن.

14

ارسال مدل به View — Strongly Typed

این مهم‌ترین بخش این قسمت است و در نسخه قبلی جزوه جا افتاده بود. روش حرفه‌ای ارسال داده به View، استفاده از Strongly Typed View است. این روش برخلاف ViewBag و ViewData، خطاها را در زمان کامپایل نشان می‌دهد و IntelliSense کامل دارد.

گام ۱: اکشن مدل را برگرداند

در Controller، مدل را به متد View() پاس بده:

C# — Controller 
public IActionResult Details(int id)
{
    var movie = new Movie
    {
        Id = id,
        Title = "Inception",
        Genre = "Sci-Fi",
        Price = 9.99m
    };
    return View(movie);
}

گام ۲: اعلان نوع مدل در View

بالای فایل View، با دستور @model نوع مدل را اعلام کن:

HTML — Views/Movies/Details.cshtml 
@model MvcMovie.Models.Movie

<h2>جزئیات فیلم</h2>

<dl>
    <dt>عنوان:</dt>
    <dd>@Model.Title</dd>

    <dt>ژانر:</dt>
    <dd>@Model.Genre</dd>

    <dt>قیمت:</dt>
    <dd>@Model.Price</dd>
</dl>

حالا @Model یک شیء از نوع Movie است. اگر پراپرتی اشتباهی بنویسی (مثلاً @Model.Titel)، Visual Studio همان لحظه خطا می‌دهد. این تفاوت بزرگ با ViewBag است که خطا را فقط زمان اجرا نشان می‌دهد.

ارسال لیست به View

اگر می‌خواهی لیستی از مدل‌ها را نمایش بدهی، از List<Movie> به‌عنوان نوع مدل استفاده کن:

C# — Controller 
public IActionResult Index()
{
    var movies = new List<Movie>
    {
        new Movie { Id = 1, Title = "Inception", Genre = "Sci-Fi", Price = 9.99m },
        new Movie { Id = 2, Title = "Interstellar", Genre = "Sci-Fi", Price = 12.99m }
    };
    return View(movies);
}
HTML — Views/Movies/Index.cshtml 
@model List<MvcMovie.Models.Movie>

<h2>لیست فیلم‌ها</h2>

<table>
    <tr>
        <th>عنوان</th>
        <th>ژانر</th>
        <th>قیمت</th>
    </tr>
    @foreach (var movie in Model)
    {
        <tr>
            <td>@movie.Title</td>
            <td>@movie.Genre</td>
            <td>@movie.Price</td>
        </tr>
    }
</table>

مقایسه چهار روش ارسال داده به View

روشتایپخطا در کامپایلکاربرد
@modelقوی‌تایپبلهتوصیه‌شده
ViewBagضعیف‌تایپخیرداده کوچک
ViewDataضعیف‌تایپخیرداده کوچک
TempDataضعیف‌تایپخیربین دو درخواست
توصیه نهایی

برای هر چیزی که «مدل اصلی صفحه» است، از @model استفاده کن. برای داده‌های جانبی کوچک مثل عنوان صفحه یا پیام موفقیت، ViewBag کافی است.

15

ViewBag و ViewData

ViewData یک دیکشنری از جفت‌های کلید-مقدار است و ViewBag همان ViewData است با یک پوسته dynamic. هر دو فقط در طول یک درخواست زنده‌اند و بعد از رندر View از بین می‌روند.

C# — Controller 
// ViewData (دیکشنری)
ViewData["Message"] = "سلام از ViewData";
ViewData["Count"] = 5;

// ViewBag (dynamic)
ViewBag.Message = "سلام از ViewBag";
ViewBag.Count = 5;
HTML — View 
<p>@ViewData["Message"]</p>
<p>@ViewBag.Message</p>

تفاوت اصلی در راحتی نوشتن است، نه در قدرت. چون ViewBag از dynamic استفاده می‌کند، IntelliSense ندارد و خطاهای نام‌گذاری فقط زمان اجرا مشخص می‌شوند. برای داده‌های خیلی کوچک (مثل عنوان صفحه یا پیام) مناسب است، اما برای مدل اصلی صفحه از @model استفاده کن.

TempData

TempData داده را برای یک درخواست بعدی نگه می‌دارد. کاربرد اصلی: بعد از RedirectToAction می‌خواهی پیام موفقیت را به صفحه بعدی ببری. در این حالت ViewBag و ViewData از بین می‌روند، اما TempData باقی می‌ماند.

C# — Controller 
[HttpPost]
public IActionResult Create(Movie movie)
{
    // ذخیره در دیتابیس
    TempData["Success"] = "فیلم با موفقیت اضافه شد.";
    return RedirectToAction("Index");
}
HTML — Index.cshtml 
@if (TempData["Success"] != null)
{
    <div class="alert alert-success">
        @TempData["Success"]
    </div>
}

نکته مهم: به‌طور پیش‌فرض، TempData وقتی خوانده شود پاک می‌شود. اگر می‌خواهی بعد از خواندن هم باقی بماند، از TempData.Keep("Success") استفاده کن.

17

Query String

Query String بخشی از URL است که بعد از علامت سؤال ? می‌آید و شامل جفت‌های کلید-مقدار است. در آدرس /HelloWorld/Welcome?name=Mehran&numtimes=3، دو پارامتر name و numtimes وجود دارند.

ASP.NET Core به‌طور خودکار این پارامترها را با پارامترهای متد اکشن تطبیق می‌دهد:

C# — Controller 
public IActionResult Welcome(string name, int numtimes = 1)
{
    ViewBag.Name = name;
    ViewBag.NumTimes = numtimes;
    return View();
}

اگر پارامتری در URL نباشد و مقدار پیش‌فرض داشته باشد، همان استفاده می‌شود. اگر مقدار پیش‌فرض نداشته باشد و پارامتر ارسال نشود، null یا مقدار پیش‌فرض نوع (مثلاً ۰ برای int) می‌گیرد.

هشدار امنیتی

داده حساس (رمز، توکن، کد ملی) را هرگز در Query String نفرست. چون در تاریخچه مرورگر، لاگ سرور و هدر Referer ذخیره می‌شود.

18

Model Binding

Model Binding مکانیزمی است که داده‌های یک درخواست HTTP را می‌گیرد و به پارامترهای متد اکشن (یا پراپرتی‌های یک مدل) تبدیل می‌کند. بدون آن باید خودت دستی از Request.Query، Request.Form یا Request.RouteValues مقدار می‌خواندی.

منابع داده

Model Binding از چهار منبع داده می‌خواند، به این ترتیب اولویت:

  1. فرم (Form)داده‌های ارسال‌شده با POST در بدنه فرم
  2. داده مسیر (Route Data)مقادیر استخراج‌شده از الگوی مسیر مثل /products/5
  3. Query Stringپارامترهای بعد از ? در URL
  4. بدنه (Body)داده‌های JSON یا XML در بدنه درخواست

مثال ساده

C# — Controller 
public IActionResult Details(int id)
{
    // Model Binding از Route Data مقدار id را پر می‌کند
    return Content($"شناسه: {id}");
}

با آدرس /Products/Details/5 و الگوی مسیر {controller}/{action}/{id?}، مقدار 5 به پارامتر id پاس داده می‌شود.

مثال پیچیده: دریافت یک مدل کامل

اگر متدی پارامتری از نوع یک کلاس داشته باشد، Model Binding سعی می‌کند همه پراپرتی‌های آن را از منابع موجود پر کند:

C# — Controller 
[HttpPost]
public IActionResult Create(Movie movie)
{
    if (ModelState.IsValid)
    {
        // movie.Title, movie.Genre, movie.Price پر شده‌اند
    }
    return View(movie);
}

اگر فرم HTML شامل فیلدهای Title، Genre و Price باشد، Model Binding خودش آن‌ها را به پراپرتی‌های متناظر در شیء Movie نگاشت می‌کند. نام فیلدهای فرم باید با نام پراپرتی‌ها (بدون حساسیت به حروف بزرگ و کوچک) یکی باشند.

خطاهای Model Binding

اگر تبدیل نوع ممکن نباشد (مثلاً در فیلد عددی متن ارسال شود)، Model Binding خطا را در ModelState ثبت می‌کند و ModelState.IsValid مقدار false برمی‌گرداند. به همین دلیل همیشه باید ModelState.IsValid را چک کنی.

اتریبیوت‌های Model Binding

وقتی نمی‌خواهی Model Binding حدس بزند داده را از کجا بخواند، از این اتریبیوت‌ها استفاده می‌کنی:

اتریبیوتمنبعکاربرد
[FromQuery]Query Stringپارامترهای جستجو، فیلتر
[FromRoute]داده مسیرشناسه‌ها در URL
[FromForm]فرم HTMLداده‌های فرم
[FromBody]بدنه درخواستJSON و XML
[FromHeader]هدر HTTPمقادیر هدر
[FromServices]DI Containerتزریق سرویس

مثال: [FromQuery]

C# — Controller 
public IActionResult Search([FromQuery] string term, [FromQuery] int page = 1)
{
    return Content($"جستجو برای '{term}' در صفحه {page}");
}

با آدرس /Products/Search?term=book&page=2 هر دو پارامتر پر می‌شوند.

مثال: [FromRoute]

C# — Controller 
[Route("products/{id:int}")]
public IActionResult Details([FromRoute] int id)
{
    return Content($"شناسه: {id}");
}

مثال: [FromBody] برای JSON

C# — Controller 
[HttpPost]
public IActionResult Create([FromBody] Movie movie)
{
    return Ok(movie);
}

این اکشن با یک درخواست POST با Content-Type: application/json و بدنه {"title":"Inception","genre":"Sci-Fi","price":9.99} کار می‌کند.

بهترین تمرین

همیشه از اتریبیوت‌های صریح استفاده کن. هم کد خودمستند‌تر می‌شود، هم جلوی حدس‌های نادرست Model Binding گرفته می‌شود.

دیباگ و Breakpoint

وقتی کد درست کار نمی‌کند، اولین ابزار دیباگ است. Breakpoint یک نقطه توقف است که به دیباگر می‌گوید «اینجا بایست تا من مقادیر را ببینم». در Visual Studio روی حاشیه سمت چپ خط مورد نظر کلیک کن تا نقطه قرمز ظاهر شود.

مراحل دیباگ

  1. Breakpoint بگذارروی خط داخل اکشن مورد نظر کلیک کن
  2. F5 بزنبرنامه در حالت Debug اجرا می‌شود
  3. درخواست را تحریک کنآدرس اکشن را در مرورگر باز کن
  4. در نقطه توقف بررسی کنمقادیر متغیرها را ببین

کلیدهای میانبر مهم

کلیدعملکرد
F5ادامه تا Breakpoint بعدی
F10اجرای خط بعدی (Step Over)
F11ورود به متد (Step Into)
Shift + F11خروج از متد (Step Out)
Shift + F5توقف دیباگ

پنجره‌های مفید

  • Locals — متغیرهای محلی متد فعلی
  • Autos — متغیرهای مهم خودکار
  • Watch — متغیرهای دلخواه که خودت اضافه می‌کنی
  • Call Stack — زنجیره فراخوانی متدها
  • Immediate Window — اجرای کد دلخواه در حین دیباگ

مشکلات رایج

اگر Breakpoint فعال نمی‌شود:

  • مطمئن شو در حالت Debug اجرا می‌کنی نه Release
  • مطمئن شو فایل ذخیره شده (نقطه سفید روی تب یعنی ذخیره نشده)
  • گزینه Just My Code را در تنظیمات دیباگ بررسی کن
  • پروژه را Clean و Rebuild کن

اگر دیباگ خیلی کند است: مطمئن شو Edit and Continue فعال است و از Breakpointهای شرطی استفاده کن (راست‌کلیک روی Breakpoint → Conditions) تا فقط وقتی شرط خاصی برقرار است متوقف شود.

نکته

برای پروژه‌های ASP.NET Core، بهتر است Breakpoint را داخل متد اکشن بگذاری، نه در Program.cs. چون Program.cs فقط یک‌بار در شروع اجرا می‌شود و بعد دیگر اجرا نمی‌شود.
