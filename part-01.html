01

.NET چیست؟

فرض کنید می‌خواهید یک خانه بسازید. برای این کار به سه چیز نیاز دارید: یک کارگاه که همه ابزارها در آن باشد، مصالح ساختمانی مثل آجر و سیمان، و کارگرانی که با آن ابزارها کار کنند. در دنیای برنامه‌نویسی هم دقیقاً همین ساختار وجود دارد و .NET نقش همان کارگاه را بازی می‌کند.

نکته‌ای که خیلی از مبتدی‌ها با آن اشتباه می‌کنند این است که .NET یک زبان برنامه‌نویسی نیست، بلکه یک پلتفرم است. تفاوت این دو مثل تفاوت کارگاه با زبانی است که کارگرها با آن حرف می‌زنند. روی پلتفرم .NET می‌توانید با چندین زبان مختلف برنامه بنویسید. معروف‌ترین این زبان‌ها C# است، اما زبان‌های دیگری مثل VB.NET و F# هم روی همین پلتفرم کار می‌کنند و همه در نهایت به یک نتیجه می‌رسند.

اجزای اصلی .NET

پلتفرم .NET از سه لایه روی هم ساخته شده که هر کدام وظیفه‌ای مشخص دارند. این لایه‌ها با هم کار می‌کنند و بدون یکی، دیگری کامل نیست.

زبان‌ها روی کتابخانه و CLR سوار هستند؛ همه با هم یک پلتفرم واحد می‌سازند

لایه اول، زبان‌ها هستند. همان‌طور که در یک کارخانه چند کارگر با تخصص‌های مختلف کار می‌کنند، در .NET هم چند زبان مختلف وجود دارد. هر زبان ویژگی‌های خاص خودش را دارد، اما همه به یک مقصد می‌رسند.

لایه دوم، کتابخانه کلاس پایه است. فرض کنید می‌خواهید خانه بسازید و به‌جای اینکه از اول همه آجرها را خودتان بسازید، از آجرهای آماده استفاده کنید. کتابخانه .NET مجموعه‌ای از کدهای آماده است که کارهای رایج را برای شما ساده‌تر می‌کند. مثلاً به‌جای اینکه خودتان کدی بنویسید که یک فایل را باز کند یا تاریخ را نشان دهد، از کد آماده استفاده می‌کنید.

لایه سوم، محیط اجرا یا CLR است. این لایه کد شما را می‌گیرد و به‌طور واقعی روی کامپیوتر اجرا می‌کند. وقتی کد C# می‌نویسید، این کد مستقیماً روی پردازنده اجرا نمی‌شود؛ اول به یک زبان میانی تبدیل می‌شود و بعد CLR آن را به زبان پردازنده تبدیل می‌کند. همین واسطه باعث می‌شود برنامه‌ها امن‌تر باشند و مدیریت حافظه خودکار انجام شود.

تاریخچه کوتاه .NET

داستان .NET از اواخر دهه ۱۹۹۰ شروع شد، وقتی مایکروسافت متوجه شد برنامه‌نویسان برای ساخت برنامه‌های ویندوزی با مشکلات زیادی دست‌وپنجه نرم می‌کنند. اولین نسخه در سال ۲۰۰۲ با نام .NET Framework منتشر شد و فقط روی ویندوز کار می‌کرد. سال ۲۰۱۶، مایکروسافت نسخه‌ای کاملاً جدید به نام .NET Core منتشر کرد که چندسکویی و متن‌باز بود. از سال ۲۰۲۰ به بعد، کلمه Core از نام حذف شد و نسخه‌ها به‌صورت سالانه با نام .NET 5، .NET 6، .NET 7، .NET 8 و... منتشر می‌شوند.

جمع‌بندی

.NET یک پلتفرم کامل است، نه یک زبان. زبان C# فقط یکی از زبان‌هایی است که روی این پلتفرم استفاده می‌شود. این پلتفرم سه لایه دارد: زبان‌ها، کتابخانه آماده، و محیط اجرا.

02

.NET Framework در برابر .NET Core

این دو را مثل دو برادر در نظر بگیرید. برادر بزرگ‌تر در سال ۲۰۰۲ به دنیا آمد و فقط در یک شهر (ویندوز) می‌تواند زندگی کند. برادر کوچک‌تر در سال ۲۰۱۶ به دنیا آمد و هر جای دنیا (ویندوز، لینوکس، مک) می‌تواند برود. هر دو از یک خانواده هستند، اما محدودیت‌هایشان کاملاً متفاوت است.

.NET Framework نسخه اول و قدیمی است که فقط روی ویندوز اجرا می‌شود، متن‌باز نیست و مایکروسافت دیگر نسخه جدیدی برایش منتشر نمی‌کند. آخرین نسخه‌اش ۴.۸.۱ است و فقط برای نگهداری پروژه‌های قدیمی مناسب است.

در مقابل، .NET Core از صفر بازنویسی شد تا سه محدودیت اصلی نسخه قبل را برطرف کند: اول اینکه روی ویندوز، لینوکس و مک اجرا می‌شود. دوم اینکه کاملاً متن‌باز است و کدش روی GitHub در دسترس همه قرار دارد. سوم اینکه سریع‌تر و سبک‌تر است و برای محیط‌های ابری و Docker طراحی شده.

چرا مایکروسافت .NET Core را ساخت؟

سه دلیل اصلی باعث این تصمیم شد. اول، دنیای برنامه‌نویسی چندسکویی شده بود و بیشتر سرورهای امروزی روی لینوکس اجرا می‌شوند؛ اگر یک فریم‌ورک فقط روی ویندوز کار کند، نمی‌تواند روی این سرورها بالا بیاید. دوم، برنامه‌های وب امروزی باید بسیار سریع باشند چون کاربران تحمل کندی را ندارند. سوم، ابزارهایی مثل Docker و Kubernetes محبوب شده بودند و برنامه‌های .NET Framework به‌سختی در این محیط‌ها اجرا می‌شدند.

03

ASP.NET Core چیست؟

فرض کنید .NET Core یک شهر بزرگ است که همه امکانات را دارد. ASP.NET Core در این شهر، ابزار ساخت مغازه است — یعنی مجموعه‌ای از ابزارهای آماده که به شما کمک می‌کند یک وب‌سایت یا وب‌سرویس بسازید. در واقع، ASP.NET Core یک فریم‌ورک است.

کلمه «فریم‌ورک» یعنی چارچوب یا قالب. فریم‌ورک مجموعه‌ای از ابزارها، قالب‌ها و کدهای آماده است که ساختار کلی برنامه را برای شما می‌سازد و شما فقط بخش‌های مخصوص برنامه خودتان را پر می‌کنید. به‌جای اینکه از صفر همه چیز را بنویسید، روی یک اسکلت آماده کار می‌کنید.

ASP.NET Core در سال ۲۰۱۶ منتشر شد و جایگزین نسخه‌های قدیمی ASP.NET شد. در نسخه قدیمی سه فریم‌ورک جداگانه برای وب‌سایت، API و صفحات ساده وجود داشت، اما در ASP.NET Core همه این‌ها در یک فریم‌ورک واحد ترکیب شدند.

جایگاه ASP.NET Core در .NET

برای اینکه دقیق بفهمید کجای این ساختار ایستاده‌اید، به نمودار زیر دقت کنید. از بیرون به داخل، هر لایه تخصصی‌تر و باریک‌تر می‌شود.

هر چه به داخل می‌رویم، تخصصی‌تر می‌شود — از پلتفرم .NET تا الگوی طراحی MVC

مزایای کلیدی ASP.NET Core

چندسکویی بودن یعنی یک بار کد می‌نویسید و می‌توانید آن را روی هر سیستم‌عاملی اجرا کنید. این ویژگی در دنیای امروز که بیشتر سرورها لینوکسی هستند بسیار مهم است. سرعت هم یکی از نقاط قوت اصلی این فریم‌ورک است؛ در بنچمارک‌های معتبر از رقبایی مثل Node.js و Django سریع‌تر عمل می‌کند. متن‌باز بودن هم یعنی می‌توانید کد منبع را ببینید و مطمئن باشید چه چیزی در حال اجراست.

دو ویژگی فنی مهم هم دارد. اول، تزریق وابستگی داخلی که در ادامه جزوه مفصل توضیح می‌دهیم؛ فعلاً بدانید این مفهوم در ASP.NET Core به‌صورت داخلی پیاده‌سازی شده و نیازی به کتابخانه خارجی ندارید. دوم، خط لوله درخواست که یعنی هر درخواست از چند مرحله عبور می‌کند و هر مرحله می‌تواند آن را بررسی، تغییر یا رد کند.

با ASP.NET Core چه چیزهایی می‌سازند؟

رایج‌ترین کاربردش ساختن وب‌سایت‌های MVC است که صفحاتشان روی سرور ساخته می‌شوند. APIهای RESTful کاربرد دوم است که برای اپلیکیشن‌های موبایل و برنامه‌های تک‌صفحه‌ای استفاده می‌شوند. با Blazor می‌توانید بخش کاربری سایت را با C# به‌جای JavaScript بنویسید. با SignalR اپلیکیشن‌های Real-time مثل چت می‌سازید و با gRPC سرویس‌های میکرو با عملکرد بالا.

04

الگوی طراحی MVC

بهترین راه برای درک MVC، تصور یک رستوران است. در یک رستوران سه بخش اصلی وجود دارد: آشپزخانه که غذا در آن آماده می‌شود، میز غذا که غذا به مشتری ارائه می‌شود، و گارسون که سفارش مشتری را می‌گیرد، به آشپزخانه می‌برد و غذای آماده را به میز می‌آورد. مشتری هیچ‌وقت مستقیم با آشپز حرف نمی‌زند؛ همیشه گارسون واسطه است.

MVC دقیقاً همین ساختار را دارد. Model (مدل) مثل آشپزخانه است — جایی که داده و منطق برنامه قرار دارد. View (نمایش) مثل میز غذاست — چیزی که کاربر نهایی می‌بیند. و Controller (کنترل‌کننده) مثل گارسون است — کسی که بین Model و View ارتباط برقرار می‌کند. وقتی کاربر درخواستی می‌فرستد، Controller آن را می‌گیرد، از Model داده می‌خواهد و در نهایت داده را به View می‌دهد تا صفحه نهایی ساخته شود.

Controller مرکز ارتباط است؛ با Model و View کار می‌کند و پاسخ را به کاربر برمی‌گرداند

سه جزء اصلی با جزئیات

Model — مغز برنامه

Model همه چیزهایی را در خود دارد که مربوط به داده و منطق است. فرض کنید یک فروشگاه اینترنتی دارید؛ اطلاعات محصولات، کاربران و سفارشات همه در Model قرار می‌گیرند. Model مشخص می‌کند یک محصول چه ویژگی‌هایی دارد (نام، قیمت، موجودی)، به دیتابیس وصل می‌شود، داده‌ها را می‌خواند و می‌نویسد، و اعتبارسنجی انجام می‌دهد. Model با زبان C# نوشته می‌شود.

View — صورت برنامه

View همان چیزی است که کاربر در مرورگر می‌بیند. تمام صفحاتی که با آن‌ها تعامل می‌کنید، همه در View قرار دارند. View با HTML، CSS و JavaScript ساخته می‌شود و در ASP.NET Core MVC معمولاً با فناوری Razor (فایل‌های .cshtml) نوشته می‌شود. این فناوری به شما اجازه می‌دهد کد C# را با HTML ترکیب کنید تا داده‌های Model به‌صورت پویا در صفحه نمایش داده شوند.

Controller — مدیر برنامه

Controller واسطه بین Model و View است. هر درخواستی که کاربر می‌فرستد اول به Controller می‌رسد. Controller تصمیم می‌گیرد کدام Model و کدام View استفاده شوند، داده را از Model می‌گیرد و به View می‌فرستد. همچنین مدیریت خطاها، اعتبارسنجی و احراز هویت هم در Controller انجام می‌شود. برای مثال، وقتی صفحه اصلی سایت را باز می‌کنید، درخواست شما به HomeController و متد Index() آن می‌رود و این متد بقیه کارها را هماهنگ می‌کند.

یک درخواست در MVC چطور پردازش می‌شود؟

فرض کنید کاربری وارد سایت فروشگاهی می‌شود و می‌خواهد لیست محصولات را ببیند. این فرآیند شش مرحله دارد:

  1. کاربر روی لینک «محصولات» کلیک می‌کند مرورگر یک درخواست به آدرس /Products می‌فرستد و منتظر پاسخ می‌ماند.
  2. Controller درخواست را دریافت می‌کند سیستم ASP.NET Core این درخواست را به ProductsController و متد Index() آن هدایت می‌کند.
  3. Controller از Model داده می‌خواهد متد Index() از Model درخواست می‌کند که لیست محصولات را برگرداند.
  4. Model داده را آماده می‌کند Model به دیتابیس می‌رود، لیست محصولات را می‌خواند و آن را به Controller برمی‌گرداند.
  5. Controller داده را به View می‌دهد Controller لیست محصولات را به View مخصوص نمایش لیست می‌فرستد.
  6. View صفحه HTML را می‌سازد View داده‌ها را داخل قالب HTML قرار می‌دهد و HTML نهایی را به مرورگر می‌فرستد تا صفحه نمایش داده شود.

چرا MVC برای پروژه‌های بزرگ مناسب است؟

مهم‌ترین مزیت MVC این است که وظایف را از هم جدا می‌کند. طراح UI فقط روی View کار می‌کند، برنامه‌نویس بک‌اند روی Model و Controller. وقتی ظاهر برنامه را می‌خواهید عوض کنید، فقط View را لمس می‌کنید. وقتی منطق برنامه تغییر کند، فقط Model و Controller تغییر می‌کنند و بقیه بخش‌ها دست‌نخورده می‌مانند.

دومین مزیت تست‌پذیری است. Model و Controller را می‌توان بدون راه‌اندازی مرورگر تست کرد و این باعث می‌شود کیفیت کد بالاتر برود. سومین مزیت کار تیمی بهتر است؛ چند نفر می‌توانند هم‌زمان روی بخش‌های مختلف کار کنند بدون اینکه تداخلی پیش بیاید.

یک نکته

برای پروژه‌های خیلی کوچک، MVC ممکن است بیش از حد ساختارمند به نظر برسد. اما برای پروژه‌های متوسط و بزرگ، همین ساختار باعث می‌شود در بلندمدت نگهداری و گسترش آسان‌تر شود.

05

تکامل ASP.NET: از WebForms تا Core

مایکروسافت در طول تاریخ سه نسل مختلف برای ساخت وب‌سایت ارائه کرده است. هر نسل درس‌های نسل قبلی را به کار گرفت و مشکلاتش را برطرف کرد. داستان این تکامل به شما کمک می‌کند بفهمید چرا الان ASP.NET Core استاندارد است.

سه نسل ASP.NET، هر کدام با درس‌گرفتن از نسل قبل

نسل اول: WebForms

سال ۲۰۰۲ بود و بیشتر برنامه‌نویسان با Windows Forms کار می‌کردند. ایده WebForms این بود که برنامه‌نویسی وب را شبیه برنامه‌نویسی ویندوز کنیم تا این برنامه‌نویسان راحت‌تر وارد دنیای وب شوند. به‌جای اینکه با HTML و HTTP سر و کله بزنند، کامپوننت‌های آماده مثل دکمه و جعبه متن را می‌گذاشتند و فریم‌ورک خودش HTML نهایی را تولید می‌کرد.

این ایده در ابتدا جواب داد، اما مشکلاتی داشت. برنامه‌نویس کنترل کمی روی HTML نهایی داشت و نمی‌دانست دقیقاً چه چیزی به مرورگر می‌رود. همچنین مفهومی به نام ViewState اختراع شد که حجم صفحات را بسیار زیاد می‌کرد. تست کردن این برنامه‌ها هم دشوار بود.

نسل دوم: ASP.NET MVC

در سال ۲۰۰۹، مایکروسافت الگوی MVC را که در فریم‌ورک‌هایی مثل Ruby on Rails موفق بود به دنیای ASP.NET آورد. این تغییر بزرگ باعث شد برنامه‌نویس کنترل کامل روی HTML داشته باشد و کد قابل تست شود. جدا شدن Model، View و Controller هم نگهداری کد را ساده‌تر کرد. اما هنوز یک مشکل بزرگ باقی بود: ASP.NET MVC فقط روی ویندوز کار می‌کرد.

نسل سوم: ASP.NET Core

در سال ۲۰۱۶، مایکروسافت تصمیم گرفت از صفر شروع کند. نتیجه، ASP.NET Core بود که همه محدودیت‌های قبلی را برطرف کرد: چندسکویی شد، متن‌باز شد، سریع‌تر و سبک‌تر شد، و برای محیط‌های ابری و Docker طراحی شد. امروز این نسخه استاندارد صنعت است.

06

HTTP و HTTPS

وقتی در مرورگر آدرس google.com را وارد می‌کنید و Enter را می‌زنید، در همان لحظه پشت صحنه اتفاقاتی می‌افتد که شما نمی‌بینید. مرورگر یک درخواست می‌سازد که می‌گوید «سلام سرور، لطفاً صفحه اصلی را برای من بفرست.» این پیام از طریق اینترنت به یکی از سرورهای گوگل می‌رسد، سرور آن را پردازش می‌کند و یک پاسخ برمی‌گرداند. مرورگر پاسخ را دریافت، تفسیر و به صفحه‌ای زیبا تبدیل می‌کند.

مرورگر درخواست می‌فرستد، سرور پاسخ می‌دهد — همه طبق قوانین HTTP

تمام این رفت و برگشت‌ها تحت قوانینی به نام HTTP انجام می‌شود. HTTP مخفف Hypertext Transfer Protocol است که کلمه به کلمه یعنی «پروتکل انتقال ابرمتن». پروتکل یعنی مجموعه‌ای از قوانین توافق‌شده، انتقال یعنی جابه‌جا کردن داده، و ابرمتن یعنی متن‌هایی که می‌توانند لینک و تصویر داشته باشند مثل صفحات وب. پس HTTP یعنی «قوانین جابه‌جا کردن صفحات وب» و زبان مشترکی است که مرورگر و سرور با آن با هم حرف می‌زنند.

یک ویژگی مهم: بدون حالت

یکی از ویژگی‌های جالب HTTP این است که بدون حالت (Stateless) است. یعنی هر درخواست مستقل است و سرور اطلاعات درخواست قبلی را نگه نمی‌دارد. فرض کنید در یک مغازه هستید؛ اگر مغازه‌دار بعد از هر خرید شما را فراموش کند، دفعه بعد باید دوباره خودتان را معرفی کنید. HTTP هم دقیقاً همین‌طور است. حالا سؤال پیش می‌آید که چطور سایتی مثل فیسبوک می‌داند شما وارد شده‌اید؟ پاسخ در مکانیزم‌هایی مثل Cookie و Session است که در قسمت‌های بعدی توضیح می‌دهیم.

HTTPS چیست؟

حالا فرض کنید می‌خواهید در یک سایت خرید کنید و شماره کارت بانکی‌تان را وارد کنید. اگر اطلاعات بدون رمزنگاری منتقل شود، هر کسی که در مسیر ارتباط باشد می‌تواند آن را ببیند. اینجاست که HTTPS وارد می‌شود. HTTPS نسخه امن HTTP است که در آن تمام اطلاعات بین مرورگر و سرور رمزنگاری می‌شود.

برای درک بهتر، این مثال را در نظر بگیرید: HTTP مثل این است که یک نامه باز بفرستید — هر کسی در مسیر می‌تواند آن را بخواند. HTTPS مثل این است که نامه را در پاکت دربسته بگذارید — تنها گیرنده می‌تواند آن را باز کند.

07

HTTP Method و Status Code

متد HTTP — نوع درخواست

هر درخواستی که به سرور می‌رود باید مشخص کند چه کاری می‌خواهد انجام دهد. این «نوع کار» را HTTP Method می‌گویند. وقتی می‌خواهید لیست محصولات را ببینید این یک GET است، وقتی می‌خواهید ثبت‌نام کنید این یک POST است، وقتی چیزی را ویرایش می‌کنید PUT یا PATCH است، و وقتی حذف می‌کنید DELETE.

Status Code — وضعیت پاسخ

سرور بعد از هر درخواست یک عدد سه‌رقمی به نام Status Code می‌فرستد که نتیجه را مشخص می‌کند. این عدد در پنج دسته کلی قرار می‌گیرد. رقم اول دسته را نشان می‌دهد: 2xx یعنی موفقیت، 3xx یعنی ریدایرکت، 4xx یعنی خطای کاربر و 5xx یعنی خطای سرور. دسته 1xx هم اطلاعاتی است و کمتر دیده می‌شود.

پنج دسته Status Code — از «همه‌چیز خوب است» تا «سرور خراب است»

کدهای 2xx یعنی درخواست شما موفق بوده. مهم‌ترینشان 200 OK است که یعنی صفحه با موفقیت بارگذاری شد، و 201 Created که یعنی یک منبع جدید ساخته شد (مثلاً بعد از ثبت‌نام موفق). کدهای 3xx یعنی منبع مورد نظر جابه‌جا شده؛ 301 یعنی انتقال دائمی و 302 یعنی انتقال موقت.

کدهای 4xx یعنی درخواست مشکل دارد. 400 یعنی داده نامعتبر است، 401 یعنی نیاز به ورود دارید، 403 یعنی وارد شده‌اید اما دسترسی ندارید، و 404 معروف یعنی صفحه پیدا نشد. کدهای 5xx هم یعنی سرور مشکل دارد؛ 500 یعنی خطای داخلی، 502 یعنی پاسخ نامعتبر از سرور واسط، و 503 یعنی سرویس موقتاً در دسترس نیست.

تفاوت GET و POST

این دو متد را زیاد با هم اشتباه می‌گیرند. تفاوت اصلی در محل قرارگیری داده است: در GET داده در آدرس URL می‌رود، در POST در بدنه درخواست. به همین دلیل GET محدودیت حجم دارد اما POST ندارد. همچنین GET قابل کش شدن است و در تاریخچه مرورگر ذخیره می‌شود، در حالی که POST این‌طور نیست.

08

HTTP Headers

وقتی بسته پستی می‌فرستید، روی آن می‌نویسید: نام گیرنده، آدرس، وزن، محتویات. این اطلاعات اضافی به پست کمک می‌کند بسته را درست به مقصد برساند. در دنیای HTTP هم دقیقاً همین‌طور است: همراه درخواست یا پاسخ، اطلاعات اضافی به‌صورت جفت‌های نام: مقدار ضمیمه می‌شود که به آن HTTP Header می‌گویند. این هدرها به سرور و مرورگر کمک می‌کنند بفهمند با چه نوع درخواستی سر و کار دارند.

ساختار یک درخواست

هر درخواست HTTP از سه بخش ساخته شده. بخش اول خط درخواست است که شامل متد (مثل GET)، مسیر (مثل /products) و نسخه پروتکل (مثل HTTP/1.1) می‌شود. بخش دوم هدرها هستند که اطلاعات بیشتری درباره درخواست می‌دهند. بخش سوم هم بدنه است که داده‌های ارسالی را در خود دارد و معمولاً فقط در درخواست‌های POST و PUT وجود دارد.

خط درخواست، هدرها، بدنه — سه بخش اصلی هر درخواست HTTP

ساختار یک پاسخ

پاسخ HTTP هم ساختار مشابهی دارد، با این تفاوت که بخش اول خط وضعیت نام دارد و شامل نسخه پروتکل، کد وضعیت و پیام وضعیت است (مثل HTTP/1.1 200 OK). بخش دوم هدرهای پاسخ هستند و بخش سوم بدنه‌ای است که محتوای واقعی مثل HTML یا JSON را در خود دارد.

خط وضعیت، هدرها، بدنه — سه بخش اصلی هر پاسخ HTTP

مهم‌ترین هدرهای درخواست

هدرهای درخواست توسط مرورگر فرستاده می‌شوند. Host دامنه و پورت سرور مقصد را می‌گوید. User-Agent اطلاعات مرورگر و سیستم‌عامل کاربر را می‌دهد. Accept می‌گوید چه نوع داده‌ای را می‌شود دریافت کرد. Accept-Language زبان مورد نظر کاربر است. Cookie کوکی‌های ذخیره‌شده را می‌فرستد و Authorization اطلاعات احراز هویت را در خود دارد.

مهم‌ترین هدرهای پاسخ

هدرهای پاسخ از طرف سرور می‌آیند. Content-Type نوع محتوای پاسخ را می‌گوید (مثلاً text/html). Content-Length حجم بدنه پاسخ را به بایت مشخص می‌کند. Set-Cookie کوکی جدیدی را از سرور به مرورگر می‌فرستد. Cache-Control تنظیمات کش را تعیین می‌کند. Location در ریدایرکت‌ها آدرس جدید را نگه می‌دارد و Date تاریخ و ساعت ارسال پاسخ را می‌دهد.
