01

آشنایی با .NET و .NET Standard

یک تشبیه ساده برای شروع

تصور کنید می‌خواهید خانه‌ای بسازید. برای این کار به چند چیز نیاز دارید: یک کارگاه که همه ابزارها در آن باشد، مصالح ساختمانی مثل آجر و سیمان، و کارگرانی که با آن ابزارها کار کنند و خانه را بسازند.

در دنیای برنامه‌نویسی هم دقیقاً همین‌طور است. .NET نقش همان کارگاه را دارد. کارگاه خودش خانه نمی‌سازد، اما همه ابزارها و مصالح لازم را برای ساخت خانه در اختیار شما می‌گذارد.

حالا اگر بخواهیم دقیق‌تر بگوییم: .NET یک پلتفرم نرم‌افزاری است که شرکت مایکروسافت آن را ساخته و همه ابزارهای لازم برای ساخت انواع برنامه‌ها را در اختیار برنامه‌نویس‌ها قرار می‌دهد.

.NET دقیقاً چیست؟

.NET یک بستر یا محیط است که شما روی آن برنامه می‌نویسید. یعنی وقتی شما یک برنامه با زبان C# می‌نویسید، این برنامه روی .NET اجرا می‌شود.

نکته مهمی که خیلی از مبتدی‌ها با آن اشتباه می‌کنند این است که .NET یک زبان برنامه‌نویسی نیست. یک پلتفرم است. تفاوت این دو مثل تفاوت «کارگاه» با «زبان حرف زدن کارگرها» است.

روی پلتفرم .NET، شما می‌توانید با چندین زبان مختلف برنامه بنویسید. معروف‌ترین این زبان‌ها C# است. زبان‌های دیگر مثل VB.NET و F# هم روی همین پلتفرم کار می‌کنند.

جمع‌بندی ساده

.NET = پلتفرم (کارگاه) + C# = یکی از زبان‌هایی که روی این پلتفرم استفاده می‌شود.

.NET از چه بخش‌هایی تشکیل شده است؟

برای اینکه بهتر درک کنید، .NET را مثل یک کارخانه بزرگ در نظر بگیرید که چند بخش مختلف دارد. هر بخش وظیفه خودش را انجام می‌دهد.

بخش اول: زبان‌های برنامه‌نویسی

همان‌طور که در یک کارخانه چند کارگر با تخصص‌های مختلف کار می‌کنند، در .NET هم چند زبان برنامه‌نویسی مختلف وجود دارد. هر زبان ویژگی‌های خاص خودش را دارد، اما همه در نهایت به یک نتیجه می‌رسند.

  • زبان C#: معروف‌ترین زبان .NET که در این جزوه از آن استفاده می‌کنیم. زبانی شی‌گرا و مدرن است.
  • زبان VB.NET: نسخه به‌روز شده زبان Visual Basic. برای کسانی که با این زبان آشنایی قدیمی دارند، راحت‌تر است.
  • زبان F#: یک زبان تابعی که بیشتر در محاسبات علمی و برنامه‌های پیچیده استفاده می‌شود.

بخش دوم: کتابخانه کلاس پایه

فرض کنید می‌خواهید یک خانه بسازید و به‌جای اینکه از اول همه آجرها را خودتان بسازید، از آجرهای آماده استفاده کنید. کتابخانه کلاس پایه .NET هم دقیقاً همین است — مجموعه‌ای از کدهای آماده که کارهای رایج را برای شما ساده‌تر می‌کند.

مثلاً به‌جای اینکه خودتان از صفر کدی بنویسید که یک فایل را باز کند، کد آماده File را استفاده می‌کنید. یا به‌جای اینکه برای نمایش تاریخ و زمان کد بنویسید، از کلاس آماده DateTime استفاده می‌کنید.

بخش سوم: محیط اجرا (CLR)

در یک کارخانه، بعد از تولید محصول، نیاز به یک بخش بسته‌بندی و ارسال دارید. CLR هم همین نقش را در .NET دارد. این بخش کد شما را می‌گیرد و آن را به‌طور واقعی روی کامپیوتر اجرا می‌کند.

CLR مخفف Common Language Runtime است. کارش این است که کد شما را از یک حالت میانی به کد قابل اجرا روی پردازنده تبدیل کند. همچنین مدیریت حافظه، مدیریت خطاها و امنیت را هم انجام می‌دهد.

نکته ساده

وقتی کد C# می‌نویسید، این کد به‌طور مستقیم روی پردازنده اجرا نمی‌شود. اول به یک زبان میانی تبدیل می‌شود، بعد CLR آن را به زبان پردازنده تبدیل می‌کند. این کار باعث می‌شود برنامه‌ها امن‌تر باشند.

تاریخچه .NET — از گذشته تا امروز

درک تاریخچه .NET به شما کمک می‌کند بفهمید چرا الان چیزهایی به نام .NET Framework، .NET Core و .NET 8 وجود دارد. داستان این‌طور شروع شد:

در اواخر دهه ۱۹۹۰، مایکروسافت متوجه شد که برنامه‌نویسان برای ساخت برنامه‌های ویندوزی با مشکلات زیادی مواجه هستند. هر برنامه نیاز به کدهای تکراری زیادی داشت. مایکروسافت تصمیم گرفت یک پلتفرم واحد بسازد که همه ابزارهای لازم را در خود داشته باشد. این پلتفرم .NET نام گرفت.

اولین نسخه در سال ۲۰۰۲ با نام .NET Framework 1.0 منتشر شد. از آن زمان تا الان، نسخه‌های زیادی منتشر شده است:

  • .NET Framework 1.0 — سال ۲۰۰۲ — اولین نسخه
  • .NET Framework 2.0 — سال ۲۰۰۵
  • .NET Framework 3.5 — سال ۲۰۰۷ — اضافه شدن LINQ
  • .NET Framework 4.0 — سال ۲۰۱۰
  • .NET Framework 4.8 — سال ۲۰۱۹ — آخرین نسخه
  • .NET Core 1.0 — سال ۲۰۱۶ — شروع یک نسل جدید
  • .NET Core 3.1 — سال ۲۰۱۹
  • .NET 5 — سال ۲۰۲۰ — حذف کلمه Core
  • .NET 6 — سال ۲۰۲۱ — پشتیبانی بلندمدت
  • .NET 7 — سال ۲۰۲۲
  • .NET 8 — سال ۲۰۲۳ — پشتیبانی بلندمدت

همان‌طور که می‌بینید، از .NET 5 به بعد، کلمه Core از نام حذف شد و فقط .NET با یک عدد نوشته می‌شود.

.NET Standard چیست و چرا به وجود آمد؟

مشکلی که به وجود آمد

در سال ۲۰۱۶ که .NET Core معرفی شد، یک مشکل جدی به وجود آمد. برنامه‌هایی که با .NET Framework نوشته شده بودند، روی .NET Core اجرا نمی‌شدند. و کتابخانه‌هایی که برای .NET Framework نوشته شده بودند، در .NET Core کار نمی‌کردند.

این مثل این بود که شما یک سری پیچ و مهره برای یک ماشین خریده باشید و بعد ماشین جدیدی بخرید که این پیچ‌ها به آن نخورد. باید همه چیز را از نو می‌ساختید.

راه‌حلی که مایکروسافت ارائه داد

مایکروسافت مفهوم .NET Standard را معرفی کرد. .NET Standard یک قرارداد مشترک است که می‌گوید: «هر کسی که .NET می‌سازد، باید این مجموعه از قابلیت‌ها را داشته باشد.»

به‌عبارت ساده‌تر، .NET Standard مثل یک زبان مشترک است. اگر کتابخانه‌ای بر اساس این زبان مشترک نوشته شود، روی همه پیاده‌سازی‌های .NET که این استاندارد را قبول دارند، اجرا می‌شود.

نکته مهم

.NET Standard یک نسخه از .NET نیست. بلکه فقط یک مشخصات فنی است. یعنی نمی‌توانید با آن یک برنامه اجرایی بسازید. فقط می‌توانید کتابخانه بسازید که در همه نسخه‌های .NET قابل استفاده باشد.

مزایای .NET Standard

  • اشتراک کد آسان: اگر کتابخانه‌ای بر اساس این استاندارد بنویسید، می‌توانید آن را در پروژه‌های مختلف .NET استفاده کنید.
  • به‌روزرسانی سریع: وقتی استاندارد به‌روز شود، همه کتابخانه‌ها به‌راحتی به‌روز می‌شوند.
  • کاهش پیچیدگی: به‌جای چند نسخه از یک کتابخانه برای هر پلتفرم، یک نسخه دارید.
توجه

از زمانی که .NET 5 معرفی شد، مفهوم .NET Standard کم‌اهمیت‌تر شده است، چون خود .NET 5 و بالاتر به‌عنوان پایه مشترک همه اپلیکیشن‌ها عمل می‌کند. با این حال همچنان در پروژه‌های قدیمی می‌توانید آن را ببینید.

02

مقایسه .NET Framework و .NET Core

داستان دو برادر

تصور کنید دو برادر دارید. برادر بزرگ‌تر در سال ۲۰۰۲ به دنیا آمده و برادر کوچک‌تر در سال ۲۰۱۶. هر دو از یک خانواده هستند، اما ویژگی‌هایشان متفاوت است. برادر بزرگ‌تر فقط در یک شهر می‌تواند زندگی کند، اما برادر کوچک‌تر می‌تواند هر جای دنیا برود.

.NET Framework و .NET Core هم دقیقاً همین وضعیت را دارند. هر دو از خانواده .NET هستند، اما یکی قدیمی‌تر و محدودتر است و دیگری جدیدتر و آزادتر.

.NET Framework — برادر بزرگ‌تر

.NET Framework اولین نسخه از پلتفرم .NET است که در سال ۲۰۰۲ منتشر شد. این نسخه مخصوص سیستم‌عامل ویندوز طراحی شده بود.

وقتی شما یک برنامه با .NET Framework می‌سازید، این برنامه فقط روی ویندوز کار می‌کند. اگر دوستتان مکینتاش داشته باشد، نمی‌تواند از آن استفاده کند. اگر سرورتان لینوکس باشد، نمی‌تواند آن را اجرا کند.

چرا این محدودیت وجود داشت؟ چون .NET Framework به‌شدت با ویندوز یکپارچه بود. این یکپارچگی باعث می‌شد برنامه‌ها بتوانند به راحتی به ویژگی‌های ویندوز دسترسی داشته باشند، اما در عوض، اجرای آن‌ها روی سیستم‌عامل‌های دیگر غیرممکن می‌شد.

آخرین نسخه .NET Framework، نسخه ۴.۸.۱ است که در سال ۲۰۱۹ منتشر شد. مایکروسافت اعلام کرده که دیگر نسخه جدیدی برای این پلتفرم منتشر نمی‌کند.

.NET Core — برادر کوچک‌تر

.NET Core در سال ۲۰۱۶ منتشر شد. این نسخه از صفر بازنویسی شد تا سه محدودیت اصلی .NET Framework را برطرف کند:

  • محدودیت سیستم‌عامل: .NET Core روی ویندوز، لینوکس و مک اجرا می‌شود.
  • محدودیت عملکرد: .NET Core سریع‌تر و سبک‌تر از .NET Framework است.
  • محدودیت استقرار: .NET Core می‌تواند در محیط‌های ابری و Docker اجرا شود.

علاوه بر این‌ها، .NET Core به‌طور کامل متن‌باز شد. یعنی کد منبع آن در دسترس همه قرار گرفت. این تصمیم باعث شد برنامه‌نویسان سراسر جهان بتوانند در توسعه آن مشارکت کنند و آن را سریع‌تر رشد دهند.

چرا مایکروسافت .NET Core را ساخت؟

دلیل اول: دنیای امروز چندسکویی است

در دنیای امروز، برنامه‌ها نباید به یک سیستم‌عامل خاص محدود باشند. اگر یک برنامه فقط روی ویندوز کار کند، نمی‌تواند در سرورهای لینوکسی اجرا شود. بسیاری از سرورهای ابری مثل AWS و Azure و همچنین سرورهای Docker روی لینوکس اجرا می‌شوند.

دلیل دوم: عملکرد بهتر نیاز بود

برنامه‌های امروزی باید بسیار سریع باشند. اگر یک سایت پربازدید کند بارگذاری شود، کاربران آن را ترک می‌کنند. .NET Core با معماری جدیدش چند برابر سریع‌تر از .NET Framework است.

دلیل سوم: نیاز به کد باز

برنامه‌نویسان دوست دارند بفهمند کدی که استفاده می‌کنند چطور کار می‌کند. .NET Framework بخش‌های بزرگی از کدش بسته بود، اما .NET Core کاملاً باز است.

دلیل چهارم: نیاز به محیط‌های ابری

امروزه همه به سمت Cloud و Docker می‌روند. برنامه‌های .NET Framework به‌سختی در این محیط‌ها اجرا می‌شوند، اما .NET Core برای این محیط‌ها طراحی شده است.

03

ASP.NET Core چیست؟

یک مثال ساده برای شروع

فرض کنید می‌خواهید یک مغازه باز کنید. برای این کار به یک ساختمان نیاز دارید. حالا فرض کنید .NET Core یک شهر باشد که همه امکانات را دارد و شما در آن زمینی دارید. ASP.NET Core در این شهر، ابزار ساخت مغازه را در اختیار شما می‌گذارد.

به زبان ساده: ASP.NET Core یک فریم‌ورک است که به کمک آن می‌توانید وب‌سایت، وب‌سرویس و API بسازید. فریم‌ورک یعنی مجموعه‌ای از ابزارها و قالب‌های آماده که کار شما را ساده‌تر می‌کند.

ASP.NET Core دقیقاً چیست؟

ASP.NET Core یک فریم‌ورک متن‌باز و چندسکویی است که توسط مایکروسافت برای ساخت اپلیکیشن‌های وب طراحی شده است. این فریم‌ورک بخشی از پلتفرم .NET Core است.

اگر بخواهیم مسیر را دقیق‌تر بگوییم:

سلسله مراتب 
.NET (پلتفرم اصلی)
  └── .NET Core (نسخه چندسکویی)
        └── ASP.NET Core (فریم‌ورک وب)
              └── MVC (الگوی طراحی داخل ASP.NET Core)

ASP.NET Core در سال ۲۰۱۶ منتشر شد و نسخه بازنویسی‌شده ASP.NET قدیمی است. در نسخه قدیمی، سه فریم‌ورک جداگانه وجود داشت: ASP.NET MVC، ASP.NET Web API و ASP.NET Web Pages. در ASP.NET Core، همه این سه در یک فریم‌ورک واحد ترکیب شدند.

ویژگی‌های کلیدی ASP.NET Core

۱. چندسکویی بودن

ASP.NET Core روی ویندوز، لینوکس و مک کار می‌کند. این یعنی شما یک بار کد می‌نویسید و می‌توانید آن را روی هر سروری اجرا کنید. این ویژگی در دنیای امروز که بیشتر سرورها لینوکسی هستند بسیار مهم است.

۲. عملکرد بالا

ASP.NET Core یکی از سریع‌ترین فریم‌ورک‌های وب در جهان است. در بنچمارک‌های معتبر، از رقبایی مثل Node.js و Django سریع‌تر عمل می‌کند. برای سایت‌های پرترافیک این سرعت حیاتی است.

۳. متن‌باز بودن

کد منبع ASP.NET Core روی GitHub در دسترس عموم است. این یعنی می‌توانید ببینید کد چطور کار می‌کند و اگر مشکلی دیدید، گزارش دهید. همچنین می‌توانید از مشارکت‌های برنامه‌نویسان سراسر دنیا بهره‌مند شوید.

۴. تزریق وابستگی داخلی

Dependency Injection یکی از مفاهیم مهم در برنامه‌نویسی مدرن است که در ادامه جزوه مفصل توضیح خواهیم داد. فعلاً فقط بدانید که ASP.NET Core این مفهوم را به‌صورت داخلی پیاده‌سازی کرده و نیازی به کتابخانه‌های خارجی ندارید.

۵. خط لوله درخواست

در ASP.NET Core، درخواست‌ها از یک خط لوله عبور می‌کنند. هر مرحله از این خط لوله می‌تواند درخواست را بررسی، تغییر یا رد کند. این معماری انعطاف‌پذیری بالایی به شما می‌دهد.

۶. یکپارچگی با فریم‌ورک‌های Front-end

ASP.NET Core به‌خوبی با فریم‌ورک‌های محبوب Front-end مثل React، Angular و Vue کار می‌کند. همچنین فریم‌ورک اختصاصی Blazor را دارد که به شما اجازه می‌دهد به‌جای JavaScript با C# Front-end بنویسید.

انواع اپلیکیشن‌هایی که با ASP.NET Core ساخته می‌شوند

  • وب‌سایت‌های MVC: سایت‌های پویا با صفحات سرور-رندر
  • Web API: سرویس‌های RESTful برای اپلیکیشن‌های موبایل و SPA
  • Blazor: اپلیکیشن‌های وب تعاملی با C# به‌جای JavaScript
  • SignalR: اپلیکیشن‌های Real-time مثل چت و نوتیفیکیشن
  • gRPC: سرویس‌های میکرو با عملکرد بالا
مهم

ASP.NET Core یک زبان برنامه‌نویسی نیست؛ بلکه یک فریم‌ورک است. ما با زبان C# کد می‌نویسیم و از ASP.NET Core برای ساخت وب‌سایت‌ها و APIها استفاده می‌کنیم.

04

الگوی طراحی MVC

تشبیه یک رستوران

بهترین راه برای درک MVC، تصور یک رستوران است. در یک رستوران سه بخش اصلی وجود دارد:

  • آشپزخانه: جایی که غذا آماده می‌شود.
  • میز غذا: جایی که غذا به مشتری ارائه می‌شود.
  • گارسون: کسی که سفارش مشتری را می‌گیرد، به آشپزخانه می‌برد و غذای آماده را به میز مشتری می‌آورد.

MVC هم دقیقاً همین ساختار را دارد:

  • Model (مدل): مثل آشپزخانه — جایی که داده‌ها و منطق برنامه قرار دارد.
  • View (نمایش): مثل میز غذا — چیزی که کاربر نهایی می‌بیند.
  • Controller (کنترل‌کننده): مثل گارسون — کسی که بین Model و View ارتباط برقرار می‌کند.

حالا اگر مشتری (کاربر) غذایی (درخواستی) سفارش دهد، گارسون (Controller) سفارش را می‌گیرد، به آشپزخانه (Model) می‌برد، آشپز غذا (داده) را آماده می‌کند، و گارسون غذا را به میز (View) می‌آورد.

کاربر درخواست را به Controller می‌فرستد و از او پاسخ می‌گیرد — View و Model هر دو تحت کنترل Controller هستند

سه جزء اصلی MVC با جزئیات

Model — مدل

Model در MVC، مغز متفکر برنامه است. هر چیزی که مربوط به داده و منطق برنامه باشد، در Model قرار می‌گیرد.

برای درک بهتر، فرض کنید یک فروشگاه اینترنتی دارید. در این فروشگاه، اطلاعات محصولات، کاربران، سفارشات و... همه در Model قرار می‌گیرند. Model مثل یک انبار بزرگ است که همه اطلاعات در آن نگهداری می‌شود.

وظایف Model:

  • تعریف ساختار داده‌ها — مثلاً یک محصول چه ویژگی‌هایی دارد
  • دسترسی به دیتابیس — خواندن و نوشتن اطلاعات
  • اعتبارسنجی — بررسی صحت داده‌ها
  • منطق تجاری — قوانین مربوط به کسب‌وکار

Model با زبان C# نوشته می‌شود. مثلاً در یک فروشگاه اینترنتی، کلاس زیر یک Model است:

C# 
public class Product
{
    public int Id { get; set; }
    public string Name { get; set; }
    public decimal Price { get; set; }
    public int Stock { get; set; }
}

View — نمایش

View همان چیزی است که کاربر می‌بیند. اگر Model مغز برنامه باشد، View صورت برنامه است. تمام صفحاتی که در مرورگر می‌بینید، همه چیزهایی که کاربر با آن‌ها تعامل می‌کند، همه در View قرار دارند.

View با HTML، CSS و JavaScript ساخته می‌شود. در ASP.NET Core MVC، Viewها با فناوری Razor نوشته می‌شوند که فایل‌هایش پسوند .cshtml دارند. این فناوری به شما اجازه می‌دهد کد C# را با HTML ترکیب کنید.

وظایف View:

  • نمایش داده‌ها به کاربر
  • دریافت ورودی از کاربر (فرم‌ها، دکمه‌ها)
  • استفاده از قالب‌های مشترک برای صفحات مختلف

Controller — کنترل‌کننده

Controller نقش مدیر یا واسطه را دارد. وقتی کاربر روی یک دکمه کلیک می‌کند یا آدرسی را وارد می‌کند، این Controller است که اول از همه درخواست را دریافت می‌کند. بعد تصمیم می‌گیرد که این درخواست به کدام Model یا View مربوط است.

برای مثال، وقتی شما صفحه اصلی یک سایت را باز می‌کنید، درخواست شما به HomeController می‌رود و متد Index() آن اجرا می‌شود. این متد داده‌های لازم را از Model می‌گیرد و به View می‌فرستد.

وظایف Controller:

  • دریافت درخواست‌های کاربر
  • تصمیم‌گیری درباره اینکه کدام Model و کدام View استفاده شود
  • ارسال داده از Model به View
  • مدیریت خطاها و اعتبارسنجی
  • مدیریت احراز هویت و مجوزدهی

نحوه کار MVC — یک مثال واقعی

فرض کنید کاربری وارد سایت فروشگاهی می‌شود و می‌خواهد لیست محصولات را ببیند. این فرآیند به این ترتیب طی می‌شود:

  1. کاربر روی لینک «محصولات» کلیک می‌کند مرورگر یک درخواست به آدرس /Products ارسال می‌کند.
  2. Controller درخواست را دریافت می‌کند سیستم ASP.NET Core این درخواست را به ProductsController و متد Index() آن هدایت می‌کند.
  3. Controller به Model مراجعه می‌کند متد Index() از Model درخواست می‌کند که لیست محصولات را برگرداند.
  4. Model داده‌ها را آماده می‌کند Model به دیتابیس می‌رود، لیست محصولات را می‌خواند و آن را به Controller برمی‌گرداند.
  5. Controller داده را به View می‌فرستد Controller لیست محصولات را به View مخصوص نمایش لیست می‌فرستد.
  6. View صفحه HTML را می‌سازد View داده‌ها را داخل قالب HTML قرار می‌دهد و HTML نهایی را به مرورگر می‌فرستد.

مزایای MVC

۱. جداسازی دغدغه‌ها

هر بخش یک وظیفه مشخص دارد. برنامه‌نویس بک‌اند روی Model و Controller کار می‌کند، طراح UI روی View. اگر یکی تغییر کند، دیگری نگران نیست.

۲. تست‌پذیری بالا

Model و Controller را می‌توان مستقل از View تست کرد. برای مثال، می‌توانید بدون راه‌اندازی مرورگر، یک Controller را تست کنید.

۳. قابلیت نگهداری

وقتی می‌خواهید ظاهر برنامه را عوض کنید، فقط Viewها را تغییر می‌دهید. وقتی منطق تغییر کند، فقط Model و Controller تغییر می‌کنند.

۴. کار تیمی بهتر

چند تیم می‌توانند همزمان روی بخش‌های مختلف کار کنند. یک تیم روی View، تیم دیگر روی Controller و تیم سوم روی Model.

معایب MVC

۱. پیچیدگی برای پروژه‌های کوچک

اگر یک پروژه کوچک و ساده دارید، استفاده از MVC ممکن است مثل استفاده از کامیون برای حمل یک بسته کوچک باشد. ساختار MVC برای پروژه‌های کوچک ممکن است بیش از حد پیچیده به نظر برسد.

۲. یادگیری زمان‌بر

برای کسی که تازه شروع کرده، درک مفاهیم MVC ممکن است کمی زمان ببرد. اما وقتی یک بار یاد بگیرید، برای همه پروژه‌ها قابل استفاده است.

نتیجه‌گیری

MVC برای پروژه‌های متوسط و بزرگ عالی است. برای پروژه‌های بسیار کوچک ممکن است بیش از حد پیچیده به نظر برسد، اما در بلندمدت استفاده از آن باعث می‌شود نگهداری و گسترش پروژه آسان‌تر شود.

05

مقایسه WebForm، MVC و Core

داستان تحول مایکروسافت در وب

مایکروسافت در طول تاریخ سه بار روش ساخت وب‌سایت را تغییر داد. هر بار با درس گرفتن از نسخه قبلی، روش جدیدی ارائه کرد. برای درک این تحول، داستان را از ابتدا می‌گوییم.

فصل اول: WebForms — شروع ساده اما پر از مشکل

سال ۲۰۰۲ بود. مایکروسافت می‌خواست ابزاری بسازد که برنامه‌نویسان ویندوزی بتوانند به‌راحتی سایت بسازند. در آن زمان، برنامه‌نویسان با Visual Basic و Windows Forms کار می‌کردند و با مفاهیمی مثل دکمه، جعبه متن و فرم آشنا بودند.

ایده WebForms این بود: «بیایید برنامه‌نویسی وب را شبیه برنامه‌نویسی ویندوز کنیم.» یعنی به‌جای اینکه برنامه‌نویس با HTML و پروتکل HTTP سر و کله بزند، فقط کامپوننت‌های آماده مثل Button و TextBox را استفاده کند.

این ایده جالب بود ولی مشکلاتی داشت:

  • کنترل کم روی HTML: شما نمی‌دانستید در نهایت چه HTML تولید می‌شود.
  • فایل‌های سنگین: مفهومی به نام ViewState اختراع شد که حجم فایل‌ها را بسیار زیاد می‌کرد.
  • تست‌پذیری ضعیف: تست کردن این برنامه‌ها بسیار دشوار بود.

با این حال، WebForms در اوایل دهه ۲۰۰۰ بسیار محبوب شد، چون برنامه‌نویسان ویندوزی به‌راحتی می‌توانستند سایت بسازند.

فصل دوم: ASP.NET MVC — بازگشت به اصول وب

سال ۲۰۰۹ بود. برنامه‌نویسان کمکم متوجه شدند که WebForms مشکلات جدی دارد. حجم صفحات زیاد است، کنترل روی HTML کم است و تست کردن دشوار است.

مایکروسافت تصمیم گرفت الگوی طراحی MVC را که در سایر فریم‌ورک‌ها مثل Ruby on Rails موفق بود، به دنیای ASP.NET بیاورد. نتیجه ASP.NET MVC بود.

مزایای ASP.NET MVC:

  • کنترل کامل روی HTML: شما خودتان مشخص می‌کردید چه HTML تولید شود.
  • تست‌پذیری بالا: می‌توانستید کد را بدون نیاز به مرورگر تست کنید.
  • جداسازی دغدغه‌ها: Model، View و Controller جدا از هم بودند.

اما ASP.NET MVC هنوز یک مشکل بزرگ داشت: فقط روی ویندوز کار می‌کرد.

فصل سوم: ASP.NET Core — بازنویسی کامل

سال ۲۰۱۶ بود. دنیای برنامه‌نویسی عوض شده بود. لینوکس سهم بزرگی از سرورها را گرفته بود. ابر و Docker محبوب شده بودند. اما ASP.NET هنوز محدود به ویندوز بود.

مایکروسافت تصمیم گرفت که از صفر شروع کند. نتیجه، ASP.NET Core بود که همه محدودیت‌های قبلی را برطرف کرد:

  • چندسکویی: روی ویندوز، لینوکس و مک.
  • متن‌باز: کد منبع در دسترس عموم.
  • سریع: چند برابر سریع‌تر از نسخه‌های قبلی.
  • سبک: مصرف حافظه بسیار کم‌تر.

06

آشنایی با HTTP و HTTPS

وقتی در مرورگر آدرس می‌زنید، چه اتفاقی می‌افتد؟

فرض کنید در مرورگر خود آدرس google.com را وارد می‌کنید و Enter را می‌زنید. در همان لحظه، پشت صحنه اتفاقاتی می‌افتد که شما نمی‌بینید:

  1. مرورگر یک درخواست می‌سازد مرورگر پیامی می‌سازد که می‌گوید: «سلام سرور گوگل، لطفاً صفحه اصلی را برای من بفرست.»
  2. درخواست به سرور می‌رود این پیام از طریق اینترنت به یکی از سرورهای گوگل می‌رسد.
  3. سرور پاسخ می‌دهد سرور گوگل پیام را دریافت می‌کند، صفحه اصلی را آماده می‌کند و به مرورگر شما می‌فرستد.
  4. مرورگر صفحه را نمایش می‌دهد مرورگر پیام سرور را دریافت، آن را تفسیر و به صفحه‌ای زیبا تبدیل می‌کند.

تمام این رفت و برگشت‌ها، تحت قوانینی به نام HTTP انجام می‌شود. HTTP زبان مشترکی است که مرورگر و سرور با آن با هم حرف می‌زنند.

HTTP چیست؟

HTTP مخفف Hypertext Transfer Protocol است. کلمه به کلمه ترجمه‌اش می‌شود «پروتکل انتقال ابرمتن».

  • پروتکل: یعنی یک سری قوانین توافق‌شده.
  • انتقال: یعنی جابه‌جا کردن داده.
  • ابرمتن: یعنی متن‌هایی که می‌توانند لینک، تصویر و... داشته باشند (مثل صفحات وب).

پس HTTP یعنی: «قوانین جابه‌جا کردن صفحات وب». این پروتکل در سال ۱۹۹۰ توسط Tim Berners-Lee ابداع شد و از آن زمان تاکنون پایه ارتباط در وب بوده است.

یک ویژگی مهم: HTTP بدون حالت است

یکی از ویژگی‌های جالب HTTP این است که بدون حالت (Stateless) است. یعنی هر درخواست مستقل است و سرور اطلاعات درخواست قبلی را نگه نمی‌دارد.

برای درک بهتر، این مثال را در نظر بگیرید: فرض کنید در یک مغازه هستید. اگر مغازه‌دار بعد از هر خرید، شما را فراموش کند، دفعه بعد که برگردید باید دوباره خودتان را معرفی کنید. HTTP هم دقیقاً همین‌طور است.

حالا سؤال پیش می‌آید که اگر HTTP بدون حالت است، چطور سایتی مثل فیسبوک می‌داند که شما وارد شده‌اید؟ پاسخ در مکانیزم‌هایی مثل Cookie و Session است که در قسمت‌های بعدی توضیح خواهیم داد.

ساختار یک درخواست HTTP

هر درخواست HTTP از سه بخش تشکیل شده است:

ساختار درخواست HTTP 
GET /products HTTP/1.1
Host: example.com
User-Agent: Mozilla/5.0
Accept: text/html

[بدنه درخواست]
  • خط درخواست: شامل متد (GET)، مسیر (/products) و نسخه پروتکل (HTTP/1.1)
  • هدرها: اطلاعات اضافی درباره درخواست
  • بدنه: داده‌های ارسالی (اختیاری، معمولاً در POST استفاده می‌شود)

ساختار یک پاسخ HTTP

هر پاسخ HTTP هم از سه بخش تشکیل شده است:

ساختار پاسخ HTTP 
HTTP/1.1 200 OK
Content-Type: text/html
Content-Length: 1256

[بدنه پاسخ: HTML صفحه]
  • خط وضعیت: شامل نسخه پروتکل، کد وضعیت و پیام وضعیت
  • هدرها: اطلاعات اضافی درباره پاسخ
  • بدنه: محتوای واقعی پاسخ مثل HTML، JSON یا تصویر

HTTPS چیست؟

حالا فرض کنید می‌خواهید در یک سایت خرید کنید و شماره کارت بانکی خود را وارد کنید. اگر اطلاعات شما بدون رمزنگاری منتقل شود، هر کسی که در مسیر ارتباط باشد می‌تواند آن را ببیند. اینجاست که HTTPS وارد می‌شود.

HTTPS مخفف Hypertext Transfer Protocol Secure است. یعنی نسخه امن HTTP. در HTTPS تمام اطلاعات بین مرورگر و سرور رمزنگاری می‌شود. حتی اگر کسی اطلاعات را رهگیری کند، نمی‌تواند آن را بخواند.

تفاوت HTTP و HTTPS

برای درک بهتر، این مثال را در نظر بگیرید:

  • HTTP: مثل این است که یک نامه باز بفرستید. هر کسی در مسیر می‌تواند آن را بخواند.
  • HTTPS: مثل این است که نامه را در پاکت دربسته بگذارید. تنها گیرنده می‌تواند آن را باز کند.

امروزه استفاده از HTTPS برای همه سایت‌ها ضروری است. حتی مرورگرها سایت‌های HTTP را «ناامن» علامت‌گذاری می‌کنند. خوشبختانه برای دریافت گواهی SSL رایگان می‌توانید از سرویس Let's Encrypt استفاده کنید.

07

Status Code و HTTP Method

یک مثال از زندگی روزمره

فرض کنید در رستوران یک غذا سفارش می‌دهید. به‌طور معمول چند حالت پیش می‌آید:

  • غذا آماده می‌شود و به شما داده می‌شود — ✅ موفقیت
  • رستوران بسته است و نمی‌توانید سفارش دهید — ❌ خطا
  • غذایی که خواستید موجود نیست — ❌ خطا
  • غذا آماده می‌شود اما باید ۱۰ دقیقه منتظر بمانید — ⏳ در انتظار

در دنیای HTTP هم دقیقاً همین اتفاق می‌افتد. هر بار که مرورگر درخواستی می‌فرستد، سرور علاوه بر پاسخ اصلی، یک عدد هم به نام Status Code می‌فرستد که وضعیت درخواست را مشخص می‌کند.

HTTP Method چیست؟

هر درخواستی که از مرورگر به سرور فرستاده می‌شود، باید مشخص کند که چه کاری می‌خواهد انجام دهد. این «نوع کار» را HTTP Method می‌گویند.

به این مثال‌ها دقت کنید:

  • می‌خواهم لیست محصولات را ببینم — این یک GET است.
  • می‌خواهم یک محصول جدید ثبت کنم — این یک POST است.
  • می‌خواهم یک محصول را ویرایش کنم — این یک PUT است.
  • می‌خواهم یک محصول را حذف کنم — این یک DELETE است.
متدمعنیکاربرد روزمره
GETدریافت دادهمشاهده یک صفحه، دیدن لیست محصولات
POSTایجاد داده جدیدثبت‌نام، ثبت سفارش، ارسال فرم

OPTIONSدریافت متدهای مجازدرخواست‌های CORS

Status Code چیست؟

همان‌طور که اشاره کردیم، سرور بعد از دریافت هر درخواست، یک Status Code می‌فرستد. این کد یک عدد سه‌رقمی است که در پنج دسته کلی قرار می‌گیرد.

دستهمحدودهمعنیمثال

دسته ۱xx — اطلاعاتی

این کدها کمتر دیده می‌شوند و معمولاً اطلاعاتی درباره مراحل انتقال می‌دهند. مثلاً 100 Continue یعنی «ادامه بده، من آماده دریافت هستم».

دسته ۲xx — موفقیت

این کدها یعنی درخواست شما با موفقیت انجام شده. مهم‌ترین آن‌ها:

  • 200 OK: درخواست موفق بود و پاسخ در بدنه است.
  • 201 Created: یک منبع جدید با موفقیت ساخته شد.
  • 204 No Content: درخواست موفق بود ولی پاسخی برای فرستادن نیست.

دسته ۳xx — ریدایرکت

این کدها یعنی منبع مورد نظر شما به جای دیگری منتقل شده است. مهم‌ترین آن‌ها:

  • 301 Moved Permanently: منبع برای همیشه منتقل شده.
  • 302 Found: منبع به‌طور موقت منتقل شده.
  • 304 Not Modified: منبع تغییر نکرده و از کش مرورگر استفاده کن.

دسته ۴xx — خطای کلاینت

این کدها یعنی درخواست شما مشکل دارد. مهم‌ترین آن‌ها:

  • 400 Bad Request: درخواست اشتباه یا ناقص است.
  • 401 Unauthorized: نیاز به ورود دارید.
  • 403 Forbidden: وارد شده‌اید اما دسترسی ندارید.
  • 404 Not Found: صفحه مورد نظر پیدا نشد.
  • 429 Too Many Requests: درخواست‌های زیادی فرستاده‌اید.

دسته ۵xx — خطای سرور

این کدها یعنی سرور مشکل دارد. مهم‌ترین آن‌ها:

  • 500 Internal Server Error: خطای داخلی سرور.
  • 502 Bad Gateway: سرور واسط پاسخ نامعتبری دریافت کرده.
  • 503 Service Unavailable: سرویس در دسترس نیست.

08

HTTP Headers

یک مثال ساده

تصور کنید می‌خواهید برای دوستتان یک بسته پستی بفرستید. روی بسته می‌نویسید: نام گیرنده، آدرس، وزن، محتویات و... . این اطلاعات به پست کمک می‌کند تا بسته را درست به مقصد برساند.

در دنیای HTTP هم همین‌طور است. وقتی یک درخواست یا پاسخ ارسال می‌شود، اطلاعات اضافی به آن ضمیمه می‌شود که به آن HTTP Header می‌گویند. این اطلاعات به سرور و کلاینت کمک می‌کند تا بفهمند با چه نوع درخواستی سر و کار دارند.

HTTP Header چیست؟

HTTP Header یک اطلاعات اضافی است که همراه با درخواست یا پاسخ HTTP ارسال می‌شود. این اطلاعات معمولاً به‌صورت جفت‌های نام: مقدار هستند.

برای مثال:

نمونه هدرها 
Content-Type: text/html
Content-Length: 1256
User-Agent: Mozilla/5.0

دسته‌بندی HTTP Headerها

هدرها بر اساس جایگاه و کاربردشان به چهار دسته تقسیم می‌شوند:

۱. هدرهای عمومی

این هدرها هم در درخواست و هم در پاسخ استفاده می‌شوند. یعنی می‌توانند در هر دو طرف ظاهر شوند.

۲. هدرهای درخواست

این هدرها فقط توسط کلاینت (مرورگر) فرستاده می‌شوند. اطلاعاتی درباره درخواست و کلاینت در اختیار سرور می‌گذارند.

۳. هدرهای پاسخ

این هدرها فقط توسط سرور فرستاده می‌شوند. اطلاعاتی درباره پاسخ و سرور در اختیار کلاینت می‌گذارند.

۴. هدرهای محتوا

این هدرها اطلاعاتی درباره بدنه درخواست یا پاسخ می‌دهند. مثلاً نوع محتوا یا حجم آن.

مهم‌ترین هدرهای درخواست

  • Host — دامنه و پورت سرور مقصد. مثلاً example.com:443
  • User-Agent — اطلاعات مرورگر و سیستم‌عامل کاربر. مثلاً Mozilla/5.0 (Windows NT 10.0)
  • Accept — نوع داده‌هایی که کلاینت می‌تواند دریافت کند. مثلاً text/html
  • Accept-Language — زبان‌های مورد قبول کاربر. مثلاً fa-IR
  • Cookie — کوکی‌های ذخیره‌شده ارسال‌شده به سرور.
  • Authorization — اطلاعات احراز هویت. مثلاً Bearer TOKEN
  • Referer — آدرس صفحه‌ای که درخواست از آن آمده.

مهم‌ترین هدرهای پاسخ

  • Content-Type — نوع محتوای پاسخ. مثلاً text/html; charset=utf-8
  • Content-Length — حجم بدنه پاسخ به بایت.
  • Set-Cookie — ارسال کوکی از سرور به کلاینت.
  • Cache-Control — تنظیمات مربوط به کش کردن پاسخ.
  • Location — آدرس جدید در ریدایرکت‌ها.
  • Server — اطلاعات سرور.
  • Date — تاریخ و ساعت ارسال پاسخ.

مثال کامل از هدرهای یک درخواست

HTTP Request 
GET /products HTTP/1.1
Host: example.com
User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64)
Accept: text/html,application/xhtml+xml
Accept-Language: fa-IR,fa;q=0.9
Accept-Encoding: gzip, deflate, br
Cookie: sessionId=abc123
Referer: https://example.com/home
Connection: keep-alive

مثال کامل از هدرهای یک پاسخ

HTTP Response 
HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
Content-Length: 12560
Cache-Control: max-age=3600
Set-Cookie: sessionId=xyz789; HttpOnly
Date: Fri, 16 Oct 2026 12:00:00 GMT
Server: nginx/1.20.0
نکته

هدرها در HTTP/1.X به بزرگی و کوچکی حروف حساس نیستند. یعنی Content-Type با content-type یکی است. اما در HTTP/2 به‌صورت اجباری با حروف کوچک نوشته می‌شوند.
